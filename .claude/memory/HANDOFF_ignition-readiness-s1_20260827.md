## 2. 무엇을 왜 고쳤나

두 구멍이 **같은 모양**이었다 — 시스템은 답을 갖고 있는데 사람이 못 본다.

**S1-a** 탐색 hold 사유가 로그에서 `held=N` 합계 하나로 뭉개져 있었다. n=56이 「차단의 52%가
소급채점 stale」을 얻으려고 prod DB `rationale` 문자열을 손으로 파싱해야 했다 — 매일 도는
크론이 매일 그 답을 갖고 있었는데도. `classify_hold_reason`/`summarize_held_by_reason`/
`format_held_by_reason` 신설 + 두 레인 result에 `held_by_reason` 파생 + **스케줄러 로그
라인에 실제 출력**. 함수 안에 `today - timedelta(days=1)`로 묻혀 있던 stale 허용 기준을
`_RETRO_ASOF_MAX_LAG_DAYS = 1`로 올리고 근거·위험을 병기(계약 부록 `[미상]` 해소).

**S1-b** catch-up이 **스케줄러 기동 시 1회**만 돌아, 그날 재시작이 없으면 결손 회차가 영영
안 돌았다. 08-26 08:45 판사 크론 결손이 그 모양이고 **아무 로그에도 안 남았다**(결손은
「없는 줄」이라 grep으로 안 잡힌다). `run_naver_inday_catchup_job`(매시 :47) 신설 —
관측·보고 잡 4종 한정, **결손 0도 매 회차 기록**.

## 3. 적대 리뷰 — 1R FAIL → 2R PASS

**P1-1(수용)**: 내가 `_INDAY_CATCHUP_MIN_LAG=30분`을 주석에 *"가장 긴 잡의 실행 시간을
넉넉히 넘긴다"*고 썼는데 **거짓이었다**. 실측: `_MAX_PER_RUN_BACKLOG=15` × 재시도 총합
(120+180+240초=9분) = **최악 135분** = 마진의 4.5배. 리뷰어가 두 스레드 동시 호출로
**같은 후보에 LLM 2회 → 최종 행 1개**(나중 커밋이 stale 스냅샷으로 덮어씀, `rejudge_count=0`
으로 흔적까지 소멸)를 재현했다.

근본 원인은 마진 값이 아니라 **보장의 부재**였다 — `last_run_at`은 성공 시에만 갱신돼
「실행 중」을 표현 못 하고, 스윕은 APScheduler를 우회해 `func()`를 직접 부르므로
`max_instances` 밖이다. ⇒ `singleflight` 락 + `SKIPPED_ALREADY_RUNNING` 표식으로 고쳤다.
**정시 크론과 catch-up 양쪽이 같은 락을 통과**해야 의미가 있다(한쪽만 잡으면 락이 장식).
생략은 성공으로 기록하지 않는다 — 기록하면 `last_run_at`이 전진해 **진짜 결손이 영영 안 돈다**.

**P2 3건 전부 채택**(각각 살아남은 변이와 짝):
- P2-1 시간당 레인 mock-free 테스트 — daily엔 있고 hourly엔 없었다. **같은 병을 두 번 낸 것**
- P2-2 `only` 필터 런타임 검증(돈 잡 2종 실제 seed)
- P2-3 성공 기록 1회 검증(없으면 매시간 무한 재실행)

## 4. ★배울 것 — 내 테스트가 처음엔 아무것도 안 지켰다

변이 「레인 말미 파생 호출 제거」가 **초판에서 살아남았다**. 표면 테스트가 레인 결과를
mock했기 때문이다 — **만드는 층이 통째로 비어 있었다**(교훈 #362의 재현). mock 없이 레인을
실제로 돌리는 테스트를 추가해 죽였고, **그 새 테스트가 곧바로 진짜 결함을 잡았다**:
실제 사유 `target_bid 없음 — 구조 결함`이 분류표에 없어 `other`로 낙하. 하나 때우면 다음
문구에서 또 새므로 **코드 전수 조사로 사유 23종 인구조사를 떠서 테스트로 고정**했다.

## 5. ⚠️ 전제 반증 (계약 §4-B ④ — 기록만, 합격기준 원문 무수정)

1,890」은 **07-21~07-30 창**의 값이다.

⇒ **배선은 라이브지만 숫자는 점화(계약 「안 하는 것」 #1) 후에야 생긴다.** 이 슬라이스가 못
