## §1 D-NAO-127 — 소재(ad) grain 외부 변경 탐지

### 결정

소재 단위 외부 변경을 `editTm`(네이버 소재 객체의 마지막 수정 시각) 앵커로 탐지해 `naver_agency_op`에 관측 기록한다. 네이버 API 쓰기는 0.

### 라이브 실측 근거 (원칙22)

`/ncc/ads` 목록 응답에 `editTm`이 UTC ISO8601로 실려 온다 — `2026-07-29T06:39:05.000Z` = 15:39:05 KST로, 폴드8와이드 되돌림 시각과 초 단위까지 일치한다. 이 확인에 추가 GET 호출은 0회(기존 수집 경로 재사용).

### 왜 editTm인가

값 비교만으로는 왕복(우리가 1,600으로 쓴 뒤 외부가 원래값 1,000으로 되돌림)이 직전 관측과 같아 무변동으로 보인다. editTm은 단조 전진하므로 편집 사실 자체가 남는다. 게다가 우리 쓰기의 `change_log.after_value`에도 그 시점의 editTm이 통째로 들어 있다(harness가 `get_ad` 응답 원본을 그대로 저장하기 때문) — 그래서 "마지막 편집이 우리 것인가"라는 판정이 문자열 동등비교 하나로 끝난다.

### 왜 change_log가 아닌가

`change_log`는 쿨다운·일일상한 계산의 원료다(`compute_change_cadence`가 action 무관하게 집계). 외부 관측을 거기 섞으면 대행사가 소재를 만질 때마다 우리 쪽 쿨다운이 연장되어, **정작 되찾으러 가야 할 순간에 우리 손이 묶인다.** 그래서 외부 변경 관측은 `naver_agency_op`라는 별도 테이블에 쌓는다.

### 구현

- 신규 SA `backend/app/services/naver_ad/ad_external_change.py` — 5단계 판정 + before 귀속 + op_type 4종(`bid_change` / `bid_mode_flip` / `status_flip` / `ad_edit`).
- 컬럼 2개, 둘 다 additive: `naver_adgroup_product.ad_edit_tm`(앵커 저장) · `naver_agency_op.occurred_at`(관측 발생 시각).
- 실행 자리: 새 크론을 만들지 않고 **실제 크론 `45 7 * * *`(07:45 KST)** 인 `shopping_ad_product_sync`에 편승했다(문서·설계 초안엔 08:20으로 적혀 있었으나 실제 크론 등록값을 확인해 정정).
- `bm_diff`의 멱등 삭제 로직을 자기 산출물로만 한정 — 프로듀서가 두 개(기존 로직 + D-NAO-127) 공존하는 상태에서 서로의 행을 지우지 않도록.
- `bm_briefing`에 소재 라벨과 실제 편집 시각을 출력하도록 확장.
- `/bm/agency-ops` API에 `occurred_at`을 노출.

### codex 리뷰

2라운드. 1R에서 P1 1건 지적 — 우리가 과거에 쓴 값이 판정 로직상 "before"로 되살아나 유령 `bid_change`로 오탐될 수 있는 경로(codex가 실행으로 재현). 수용·수정 → 2R "P1 해소, 배포 차단 없음".

### 신규 안전장치 4종

1. **자동 하향 일일 상한 3회**(`_MAX_DAILY_AUTO_BID_DOWNS`). DL3 면제(하향 무제한)는 "사람이 매 스텝을 본다"는 것을 전제로 만든 규칙인데, 이걸 무인 자동 경로에 그대로 쓰면 하루 8스텝까지 파고들 수 있다(0.85⁸ ≈ 27%까지 절단). 사람이 승인한 하향은 종전 면제를 그대로 유지한다. ★세는 원료를 잘못 고르면 역효과다 — "그 소재의 오늘 모든 변경"을 세면 사람이 손으로 만진 소재에서 정작 자동 손실 하향이 종일 막힌다. 그래서 세는 것은 **자동 하향 성공 건수**(`change_log ⨝ proposal`)로 한정했다.
2. **대상 단위 원자 클레임**. 클레임을 한 문장의 UPDATE로 처리하고 `NOT EXISTS(같은 소재 executing)`를 그 안에 넣었다. 레인의 사전 조회 방식은 조회와 생성 사이에 창이 열려 원자적이지 않다. ⚠️현재 prod는 SQLite 쓰기 직렬화를 전제로 성립한다 — PostgreSQL로 이전하면 행 잠금이 별도로 필요하다.
3. **킬스위치 2중 재검사**(harness 진입 시점 + writer 호출 직전 시점). 단 `is_auto_exec()`로 판정을 감싸 **사람이 console에서 직접 승인한 것은 스위치와 무관하게 통과**시킨다 — 사고 대응 중에 자동화를 꺼도 사람은 여전히 직접 조작할 수 있어야 하기 때문(codex가 1R 수정의 회귀로 이 문제를 잡아냈다).
4. **레인당 blast radius 5건**(`_MAX_AD_AUTO_EXEC_PER_LANE`). 상한을 넘는 제안은 드롭이 아니라 Confirm 대기로 강등되고, 매시간 쌓이지 않도록 만료 교체 방식으로 처리한다.

### 롤백

**열린 것의 정체(안전 핵심)**: 소재 UP은 rank-step 분기에 안 걸려 레거시 ±15% `_clamp_step` 폴백을 탄다 → 열린 것은 **클램프가 걸리는 `bid_up` 하나**. 클램프 면제 타입(`bid_up_servo`/`rank`/`cold`/`explore`)의 (승인원⟺타입) 쌍방향 잠금은 불변(300원→90,000원 구멍을 잡은 자리) — 이 불변식은 테스트로 고정했다.

### codex 적대 리뷰 5라운드 — P1 총 12건 전건 대응

라운드별 P1 건수: 1R 4건 → 2R 3건 → 3R 2건 → 4R 3건(+설계 권고) → 5R 3건.

**추가된 안전장치 6종**:

1. **쓰기 CAS** — 가드레일 판정 기준가와 PUT 직전 실측이 다르면 쓰지 않는다(오늘 15:39 대행사가 폴드8와이드를 1,600→1,000으로 되돌린 것이 정확히 이 부류). ★한계 명시: 네이버 API에 조건부 쓰기가 없어 원자적 CAS가 불가능 — 잔여 창은 왕복 1회.
2. **PUT body 최신화** — 첫 GET 스냅샷으로 body를 만들면 그 사이 외부가 켠 `useGroupBidAmt`를 우리가 조용히 되돌린 뒤 성공으로 기록한다(사후 탐지도 "우리 쓰기"로 분류돼 아무도 못 잡는다).
3. **자동 상향 누적 상한 2.0배** — 기준점은 시간창이 아니라 **사람 개입 또는 외부 변경**으로만 재설정한다. ★실패 기록: 초판은 7일 창이라 만료 때마다 천장이 스스로 올라가 800→1,600→3,200→…→100,000이 됐고, 그 우회를 내 테스트가 계약으로 고정하고 있었다. 중간에 min(기준점, 현재값)으로 풀려다 기준점이 현재값을 따라 올라가 **상한이 영영 안 걸리는** 상태를 만들었고, 회귀 테스트가 이를 잡았다.
4. **쓰기 직전 외부변경 확인 (fail-CLOSED)** — 하루 1회 탐지에 기대면 우리가 먼저 쓰는 순간 editTm이 우리 것으로 바뀌어 외부 사건이 영구 소실된다. 매 판정마다 live `(editTm, bidAmt)`를 우리가 아는 상태 집합과 대조하고, **확인이 성립하지 않으면 자동 상향을 보류**한다. 관측 기준선이 없으면 그 자리에서 세우고 다음 회차부터 개방. 하향·사람 승인은 이 게이트 대상이 아니다.
