## 1. Python 3.14 + SQLAlchemy 호환성 이슈

### 이슈
SQLAlchemy 2.0.40에서 `Mapped[str | None]` 사용 시 `TypeError: descriptor '__getitem__' requires a 'typing.Union' object` 에러 발생. Python 3.14의 typing 내부 변경으로 `Union.__getitem__` 동작이 달라짐.

### 해결
1. SQLAlchemy 2.0.48로 업그레이드
2. `from __future__ import annotations` 추가
3. `str | None` 대신 `Optional[str]` 사용

### 교훈
Python 3.14는 아직 최신이라 라이브러리 호환성 이슈가 있을 수 있음. SQLAlchemy는 반드시 2.0.48 이상 사용할 것. 새 Python 버전 사용 시 첫 마이그레이션에서 호환성을 바로 검증해야 함.

## N. 조망 원가 0 — "데이터 없음"이 아니라 "엉뚱한 원천" (2026-06-03, D-12)

### 🐛 이슈
종합조망 순이익에 원가가 거의 미반영(253옵션 중 201옵션 0원). "쿠팡 supplyPrice가 빈값이라 어쩔 수 없다"고 단정할 뻔함. 새 페이즈(P3/P5)를 더 쌓아도 이 구멍은 그대로였을 것.

### ✅ 해결
코딩 전 라이브 진단(읽기전용 SQL, 서버 DB)으로 원인을 사실로 확정 → 원가는 **이미 내부 product_master.cost_price에 792상품(89%) 있었고**, product_channel_mapping(coupang) 다리로 실거래 118옵션(66%)에 닿았다. 결합엔진이 coupang supply_price(0.6% 커버)만 보던 게 원인. 엔진 읽기측 조인을 내부 원가 다리로 바꿔 원가 0→468,313 반영(순이익 과대계상 교정). 신규 테이블·쿠팡호출 0.

### 📌 교훈
"데이터가 없다"고 단정하기 전에, **다른 원천에 이미 있는지 라이브로 진단**하라(원칙22). 특히 같은 시스템이 다른 경로(기존 회계엔진 profit_calculator)로 이미 그 데이터를 쓰고 있으면 거의 확실히 어딘가 있다. 진단 스크립트(diag_coverage.py·diag_bridge.py)로 "현재 원천 커버리지 vs 잠재 원천 커버리지"를 숫자로 비교하면 헛수고를 막는다. 부수: 확정 결정(D-10 saleAgentCommission 기준선)도 라이브에서 전제가 깨질 수 있으니(전부 0) 실데이터로 검증.

## N. 감사 "이상 0건"이 정상이 아니라 "비교 0건"일 수 있다 (2026-06-03, D-13)

### 🐛 이슈
P4 수수료 감사가 "anomaly 0"이라 잘 작동하는 줄 알았으나, 실제로는 기준선(saleAgentCommission)이 201옵션 전부 0이라 `registered<=0`에서 즉시 스킵 → **비교가 한 건도 안 일어남**. "0 이상"은 "전부 정상"이 아니라 "감사 부재"였다.

### ✅ 해결
기준선 데이터 실태를 라이브로 확인(전부 0). 기준선을 옵션 자기 정착 실측율(service_fee_ratio mode)로 교체(D-13). 검증 시 "정상 데이터→0" 뿐 아니라 **합성 이상 주입→플래그 1**을 반드시 확인해 감사가 실제로 비교하는지 증명. stats에 fee_options_checked(비교 시도 수)를 추가해 "비교 0건"과 "비교 후 0"을 구분 가능하게 함.

### 📌 교훈
감사/검증 로직의 "이상 0건" 결과는 **비교가 실제로 일어났는지** 먼저 확인하라(원칙22). 0이 나오면 "정상 0"인지 "스킵 0"인지 구분하는 카운터(시도 수)를 둬라. 검증은 정상→음성뿐 아니라 **합성 양성 주입→양성**으로 탐지력을 증명해야 한다(원칙14). 확정 결정(D-N)의 전제도 라이브에서 깨질 수 있으니 기준선 데이터 실태부터 본다.

## 2. 네이버 클레임 쓰기 API 스펙 함정 — 철자·필드형이 직관과 다름

### 🐛 이슈
N7 wave2 반품 5종 구현 중, 네이버 API센터 실측 스펙이 직관과 어긋나는 지점이 있었다.
- 반품 보류 유형 enum에 `EXTRAFEEE`(E 3개)가 있다 — 오타처럼 보이지만 **원문 그대로**다. "고쳐서" EXTRAFEE로 보내면 거부될 위험.
- 반품 거부 사유 `rejectReturnReason`은 **자유 텍스트**인데, 취소 직접요청 `cancelReason`은 **enum**이다. 같은 "클레임 사유"라도 엔드포인트마다 enum/자유텍스트가 갈린다.
- 반품 수거 배송방법 `collectDeliveryMethod` enum은 발송용 `deliveryMethod`와 달리 RETURN_DELIVERY/RETURN_INDIVIDUAL/RETURN_MERCHANT/UNKNOWN을 포함 — 발송용 상수를 재사용하면 안 됨(별도 _VALID_COLLECT_DELIVERY_METHODS 신설).

### ✅ 해결
전부 API센터 스크린샷 실측만 사용(추측 금지). docs/references/14에 enum·철자 원문대로 기록(EXTRAFEEE 옆에 "★철자 원문대로" 주석). 수거 배송방법은 발송용과 별도 상수로 분리. 빌드/임포트/codex(P1·P2 0)/prod dry_run·검증400으로 확인.

### 📌 교훈
외부 API enum은 "오타로 보여도 고치지 말고" 실측 그대로 쓴다(원칙: 추측 금지). 비슷한 이름의 필드(cancelReason vs rejectReturnReason, deliveryMethod vs collectDeliveryMethod)라도 형(enum/자유텍스트)·허용값이 다를 수 있으니 **엔드포인트별로 스펙을 따로 확인**하고 상수를 재사용하지 마라. 스크린샷이 길어 잘리면(택배사 100+ 테이블 아래 송장/수량 필드) "이게 끝인가" 단정 말고 잘린 뒷부분을 반드시 확인한다.

## 3. 네이버 교환 쓰기 API — 반품과 닮았지만 필드명·제약이 미묘하게 다름

### 🐛 이슈
N7 wave3 교환 5종 구현 시 반품(wave2)과 구조가 거의 같아 그대로 복사하고 싶은 유혹이 있었으나, 실측 스펙이 미묘하게 달랐다.
- 경로가 `claim/exchange/*` (반품은 `claim/return/*`). 수거완료는 `claim/exchange/collect/approve`로 한 단계 더 깊다.
- 교환 보류 상세사유 필드명 = `holdbackExchangeDetailReason`, 추가비용 = `extraExchangeFeeAmount` (반품은 holdbackReturnDetailReason / extraReturnFeeAmount). holdbackClassType enum만 동일.
- 교환 재배송(dispatch)은 reDeliveryMethod/Company/TrackingNumber 3필드가 **전부 optional**(BODY는 required이나 개별 필드는 REQUIRED 배지 없음). N6 발송(dispatch)은 DELIVERY에 택배사+송장 필수였던 것과 대조.

### ✅ 해결
필드명은 실측대로 분리(Exchange 접미사). codex가 "재배송에 DELIVERY 시 택배사+송장 XOR 강제는 스펙에 없는 앱 제약"이라 지적 → 대화형 검증 후 합의 수용(원칙19): N6 dispatch와 다른 엔드포인트이고 실측상 전 필드 선택이므로 XOR 제거, 부분입력은 그대로 보내고 네이버가 검증. enum 상수(holdbackClassType, deliveryMethod)는 반품 것 재사용.

### 📌 교훈
"비슷한 API"일수록 **복붙 후 필드명·경로·필수여부를 1:1로 재대조**하라. 같은 개념(보류 상세사유)도 클레임 종류마다 필드명이 다르다(Return/Exchange). 한 엔드포인트(N6 발송)에서 필수였던 조건이 유사 엔드포인트(교환 재배송)에선 선택일 수 있으니 이전 구현의 제약을 그대로 이식하지 마라 — 스펙에 없는 제약은 유효 요청을 막는다. codex가 "스펙에 없는 앱 제약"을 지적하면 추측금지 원칙상 대체로 수용이 맞다.

## 4. 네이버 N8 상품 쓰기 — prod 실측으로 범위를 줄이는 게 안전 (옵션 미사용·가격 묶임)

### 🐛 이슈
N8 "재고·가격·수정·등록 전부" 요청을 그대로 다 구현하려다, API센터 스펙과 prod 데이터를 보고 두 가지를 발견.
- "상품 옵션 재고 변경"(option-stock) API는 이름과 달리 `salePrice`가 REQUIRED라 재고만 바꿔도 가격을 함께 보내야 함 → read-modify-write 안 하면 가격 손실 위험. 게다가 옵션별(optionCombinations/optionStandards) 페이로드 필요.
- prod 상품 1,202개 실측: 오하이는 원상품(origin_product_no)당 재고 1개, 변종은 group_product_no로 묶인 **별도 원상품**(= 옵션 미사용). 옵션별 재고 API가 애초에 불필요.
- 반면 "판매 상태 변경"(change-status)은 가격을 전혀 안 받고 원상품 단위 재고/상태(SALE/OUTOFSTOCK/SUSPENSION)를 처리 → 품절/재입고/판매중지를 가격 위험 0으로 커버.

### ✅ 해결
Jino와 대화로 범위를 2단계 축소(D-11): 수정·등록 제외(라이브 상품 손상 위험) → 옵션재고도 제외(미사용+가격위험) → **change-status만** 구현. codex 1차 P1×2/P2×3 전부 합의 수정(OUTOFSTOCK→재고0 강제, SALE→재고≥1, 클라 enum allowlist, 전이규칙 위반까지 막는 NAVER_STATUS_TRANSITIONS, 타입 union) → 2차 pass. prod dry_run 7케이스 라이브 통과.

### 📌 교훈
"전부 구현해줘" 요청이라도 **API 스펙 실측 + 실데이터 프로브로 진짜 필요/위험을 먼저 확인**하면 범위가 줄어든다(원칙22). 특히 외부 쓰기 API는 이름(옵션 재고 변경)과 실제 동작(가격까지 필수)이 다를 수 있으니 필수 필드를 꼭 본다. 같은 목적(재고 관리)을 더 안전한 엔드포인트(가격 안 받는 change-status)로 달성할 수 있으면 그쪽을 택한다. 전이 규칙이 있는 상태머신 API는 현재상태별 유효 전이만 UI에 노출해 무효 요청(네이버 400)을 사전 차단한다.

## 5. E1a expert_desk(T1~T9) — SQLAlchemy 스크립트 함정 + 프론트 라이브 프리뷰 안전 절차

### 🐛 이슈
- 독립 파이썬 스크립트에서 `from app.database import Base, engine; Base.metadata.create_all(engine)`만 실행하면 **테이블이 0개** 생성된다. `app.models`를 명시적으로 import하지 않으면 SQLAlchemy declarative 등록(모델 클래스가 `Base`에 자신을 등록하는 부수효과)이 일어나지 않아 `Base.metadata`가 비어 있다. pytest에서는 항상 `from app.models import X, Y`를 같이 import해서 이 함정을 못 느꼈다.
- 프론트 시각 검증을 위해 `app.main:app`(전체 앱)을 그대로 띄우면 `lifespan`이 `start_scheduler()`를 호출해 real APScheduler가 진짜 크론(외부 API 크레덴셜 사용)까지 등록한다 — 스크래치 DB로 프론트만 확인하려던 의도와 달리 실제 외부 호출 위험을 안게 된다.
- `mcp__Claude_Preview__preview_start`용 `.claude/launch.json`은 **작업 대상 워크트리가 아니라 이 세션 자체의 워크트리**(`.claude/worktrees/<session>/.claude/launch.json`)에 있어야 인식된다 — 코드가 있는 워크트리에 만들면 "launch.json 없음" 에러가 난다.

### ✅ 해결
- 스크립트에서 `Base.metadata.create_all` 전에 반드시 `from app import models  # noqa: F401`을 먼저 import.
- 프론트 프리뷰는 필요한 라우터만 마운트한 미니 FastAPI 앱(`app.include_router(naver_ad.router)`만, `app.main`의 `lifespan`/스케줄러 없이)을 임시로 만들어 사용 — 스크래치 DB에 대해서도 외부 API 부작용이 전혀 없게 격리.
- launch.json은 `runtimeExecutable`을 다른 워크트리 경로의 wrapper 스크립트나 `bash -c "cd '<target>' && ..."`로 지정해, 세션 워크트리에 두고 실제 코드는 작업 워크트리를 가리키게 한다.
- prod 사본 검증 시 대상 테이블(NaverProposal)이 비어 있으면 "생성 파이프라인 자체가 prod에 배포된 적 없다"는 신호일 수 있다(추정 금지 — 코드 버그로 오판하지 않고 먼저 배포 이력을 재확인) — 이럴 땐 상위 파이프라인(proposal_pipeline)을 같은 사본에서 먼저 돌려 실제 데이터를 만든 뒤 하위 기능(expert_desk)을 검증한다(89K 재검증 때와 동일 원칙).

### 📌 교훈
독립 스크립트로 SQLAlchemy 모델을 다룰 때는 **모델 모듈을 명시적으로 import했는지 항상 확인**한다(pytest의 암묵적 import에 기대지 마라). 스크래치 DB로 프론트를 검증할 때도 백엔드 진입점을 있는 그대로 쓰지 말고 **필요한 라우터만 마운트한 최소 앱**을 만들어 외부 부작용 표면을 원천 차단한다. `preview_start`의 `launch.json`은 세션 워크트리 기준이라는 것을 기억한다. prod 사본 검증에서 "데이터가 없다"는 관찰은 버그가 아니라 **배포 상태에 대한 실측 정보**일 수 있으니 코드를 의심하기 전에 그 가능성부터 확인한다.

## 6. 워크트리에만 사는 기록물은 조용히 소실된다 — 인덱스에서 지우기 전 원본 실존 확인

CD4 학습층은 세분화 판사(LLM)의 판정 근거를 볼트에 남겨야 했다(D-58-12 명문). 구현은 근거를 관례대로 `after_value`(구조화 JSON)에 담았고, 단위 테스트(after_value 검증)는 통과했다. 그러나 볼트 렌더러 `vault_export._render_diary_day`는 observe 행을 **`e.rationale`만** 출력한다(execute/blocked 행만 before→after 컬럼 렌더). 즉 after_value에 넣은 판정 근거는 **테스트는 녹색인데 볼트에는 절대 안 보이는** 상태 — 매일 LLM 비용을 쓰고 산출물을 버리는 격리↔라이브 갭. 리뷰어(P2-1)가 렌더 경로를 실제로 열어보고 잡았다.

### ✅ 해결
근거를 **소비자가 읽는 필드(`rationale`)** 에 마크다운 블록으로 넣고(split 셀·축·근거 인라인), 기계판독용 상세는 after_value에 병기. 회귀 테스트도 "테이블 스키마에 값이 있다"가 아니라 "**렌더러가 출력하는 필드에 그 문자열이 있다**"를 단언하도록 작성.

### 📌 교훈
**"DB에 저장했다"는 "사용자가 본다"가 아니다.** 산출물을 어떤 뷰가 소비한다면, 저장 전에 그 뷰의 렌더 코드를 열어 **실제로 읽는 필드**를 확인하고 거기에 넣어라. 테스트는 스키마 존재가 아니라 렌더 경로를 단언해야 이 갭을 잡는다(원칙22의 격리↔라이브를 코드 내부에서 재현하는 축소판 — 저장 경로는 통과하나 표시 경로는 비어 있다). 리뷰 체크 질문: "이 값을 누가 읽는가? 그 읽는 코드가 실제로 이 필드를 참조하는가?"

## 14. stop_observe·INFO 미기록 = 침묵 분기의 관측 갭 — "기록 없음"을 "평가 안 됨"으로 오독하지 말 것 (2026-07-22, D-NAO-83 VF 라이브 검증)

### 📌 교훈

## 15. 로그 레벨만 고쳐선 안 보이는 카운터 — "레벨 소실"과 "라인에 없음"은 별개 갭 (2026-07-23, D-NAO-85 관측 갭 수리)

## 17. 절대 날짜로 시드한 테스트가 하니스 기본값(오늘)과 어긋나 flaky — monkeypatch는 호출되는 모듈에 걸 것 (2026-07-23, BM 벤치마크 flaky 수정)

**테스트에 하드코딩된 절대 날짜가 하니스 기본값(오늘)과 어긋나면 시간이 지나 반드시 터진다.** 하니스 경유 테스트는 (a) `kst_today`를 **소비(호출) 모듈**에서 monkeypatch하거나 (b) 시드를 `kst_today` 상대 날짜로 작성할 것 — 이 둘 중 하나가 아니면 "오늘 우연히 통과"하는 시한폭탄이 된다. monkeypatch는 반드시 함수가 **정의된 곳이 아니라 호출되는 모듈**의 심볼에 걸어야 한다(`unittest.mock.patch` 표준 함정과 동일 원리).

## 19. pause 직후 관측 함정 — 로컬 entity status는 다음 아침 sync까지 stale (2026-07-20)

plist의 `__PYTHON__`/`__SCRIPT__` 자리표시자가 영영 치환되지 않는다. plist 헤더가 안내한 `cp + launchctl load`
그대로 하면 launchd가 실행 파일을 못 찾고 `KeepAlive` + `ThrottleInterval 10`으로 10초마다 재시도하는
크래시 루프가 된다. 결과: WING2 RG 갱신 요청을 아무도 claim하지 않는다 = **스프린트 전체가 라이브에서 死코드**.
codex가 [P1]으로 잡았다(우리 테스트는 전부 초록이었다 — 유닛/HTTP 테스트는 launchd 설치 경로를 안 본다).

### ✅ 해결
- 설치 loop에 `wing2:wing_browser_fetcher.py` 편입(같은 스크립트를 env로 인스턴스 분리하는 D-7 패턴).
- 설정 파일(`~/.ohisell_wing2_fetcher.json`) 없으면 건너뛰되, **그냥 건너뛰지 않고 bootout + plist 삭제**까지 —
  안 그러면 예전에 수동 설치했거나 나중에 설정을 지운 Mac에서 크래시 루프가 살아남는다(codex R2).
- 그 bootout도 **확인한다**: `2>/dev/null || true`는 실패해도 조용하다. 검증 없이 성공을 출력하고 plist까지
  지우면 루프는 그대로인데 화면만 깨끗해지고 다음 실행이 문제를 볼 근거마저 사라진다 → 같은 파일의 구
  supervisor 정리 패턴(bootout → 25초 소멸 대기 → 재확인 → 잔존 시 `exit 1`) 재사용, 잔존 시 plist는 남긴다(codex R3).
- plist 헤더의 설치 안내를 `cp + load`(자리표시자 잔존)에서 `bash tools/install_local_runtime.sh`로 교체.

### 📌 교훈
**데몬/크론/launchd 잡을 새로 만들면 "설치 경로에 편입됐는가"가 완료 기준의 일부다.** 파일을 만든 것은
배포가 아니다 — 원칙 22의 "라이브 증거"가 코드뿐 아니라 **기동 경로**에도 적용된다. 자동 테스트가 절대 못
보는 층이라 리뷰에서 명시적으로 물어야 한다: *이 잡은 어떤 명령으로 설치되며, 그 명령이 이 잡을 알고 있는가?*
자매 교훈: 정리(cleanup) 코드는 **"내렸다"고 말하지 말고 내려간 것을 확인**해야 한다. 관측을 지우는 정리는
문제를 고치는 게 아니라 숨긴다.

### 🔁 부수 패턴 — 성공/실패 비대칭
같은 리뷰에서 [P2]로 나온 것: 판매분석 실패 보고(`mark_fetch_error`)만 계정 차원이고 성공
(`_mark_heartbeat`)은 계정 무구분이었다 → WING2 ingest가 WING1 행에 성공을 찍고 WING1의 실패 흔적까지
지운다. **상태를 계정(또는 어떤 차원이든)으로 쪼갤 때는 성공 경로와 실패 경로를 같이 쪼갠다** — 한쪽만
쪼개면 남의 성공이 내 신선도가 되는 조용한 위조가 생긴다.

## 45. "쓰기 경계에서 재검증"은 마커에 **다른 양**을 담아야 성립한다 — 아니면 동어반복 (2026-07-27, CS 스프린트 PR #123, 리뷰 2R)

### 🐛 이슈
±15% 완전 면제 타입(`bid_up_cold`)의 유일한 가격 브레이크로, 레인이 산정한 상한을
`expected_effect` 마커에 실어 보내고 harness 쓰기 경계에서 재검증하게 했다(탐색
`explore_ceiling` 관례 그대로). 그런데 마커에 **`target_bid`를 담았다.**
`target_bid = min(이익상한, 시장가)`이므로 경계 검사 `if target_bid > cold_ceiling`은
**`X > X` = 영원히 False**. 게이트가 실제로 거르는 것은 "마커가 있느냐" 하나뿐이었고,
"레인이 상한을 제대로 씌웠나"는 **아무것도 검증되지 않았다**.
더 나쁜 것: 내가 쓴 테스트가 `assert decode_cold_ceiling(p.expected_effect) == p.target_bid`로
**그 동어반복을 명세로 고정**해 버렸다 — 테스트가 결함을 지키는 형국.
적대적 리뷰 2R이 공격 12종 중 11종은 차단됨을 확인하고, 마커==target_bid==90,000짜리 제안
하나만 통과하는 것을 잡아냈다.

### ✅ 해결
마커에 **경제 상한(`ceiling_cpc`, 저신뢰 할인 적용 후)** 을 담도록 변경 — `target_bid`와 서로
다른 양이 된다. 선례 확인: 탐색도 `target = min(target, ceiling)` **뒤에** `ceiling`을 담는다.
회귀 테스트를 "마커 != target_bid" + "레인 클램프 버그를 흉내낸 제안(마커 1390 / target_bid
3000)이 `real_write_blocker`와 `execute` 양쪽에서 죽는지"로 교체.

### 📌 교훈
- **재검증 게이트의 두 피연산자가 같은 값에서 파생되면 그 게이트는 존재하지 않는 것과 같다.**
  마커에 담을 값을 고를 때 "이 검사가 False가 아닌 경우가 실제로 있나?"를 먼저 자문할 것.
- **이 게이트가 막는 것은 악의적 제안이 아니라 우리 레인의 버그다.** 악의는 승인원 잠금이
  막는다. 그래서 마커는 "레인이 자기 계산을 스스로 신고하는 값"이 아니라 "그 계산의 **입력
  제약**"이어야 한다.
- **테스트가 결함을 명세로 굳힐 수 있다.** 구현을 그대로 반사하는 단언(`assert f(x) == x`)은
  회귀 방어가 아니라 회귀 고정이다. 단언은 "무엇이 참이어야 하는가"에서 출발해 쓸 것.
- 선례가 있는 패턴을 복제할 때는 **형태만 베끼지 말고 그 패턴이 무엇을 검증하는지**를 확인할 것
  (탐색 마커는 `min()` 뒤에 ceiling을 담는다 — 그 순서 자체가 설계였다).

## 45. 외부 API의 파생 필드로 원본 필드를 역추론하지 마라 — 같은 값에 여러 원인이 접힌다 (2026-07-28, D-NAO-97)

### 🐛 이슈
`entity_sync`가 캠페인의 `userLock`(사람의 On/Off 스위치)을 **`status=="PAUSED"`로 역추론**했다.
그런데 네이버의 `status`는 사람 조작 말고도 **일예산 소진·검수 중·상위 정지·비즈채널 이상**으로
PAUSED가 된다. 결과: 03 캠페인이 일예산 5만원을 소진해 네이버가 자동정지시킨 것을
`external_status_change`("외부(MOP/사람) 상태 변경")로 기록(prod change_log id 847).
"대행사가 우리 캠페인을 만졌다"는 **유령 신호**가 운영 판단을 오도한다.

원본 필드(`userLock`)와 원인 필드(`statusReason`)는 **API 응답에 처음부터 있었다.** fetcher가
안 넘겼을 뿐이다. 같은 파일의 그룹·키워드 경로는 처음부터 `userLock`을 그대로 써서 오탐이 없었다 —
**한 계층만 다르게 구현된 비대칭이 결함의 전부**였다.

### ✅ 해결
- 캠페인도 `userLock`으로만 판정(역추론 삭제). `user_lock` 키가 **아예 없는** 레거시 입력만 옛 규칙
  폴백 — "없는 정보를 False로 지어내면" 사람이 끈 캠페인이 on으로 뒤집혀 반대 방향 유령이 생긴다.
- 시스템 사유 정지는 **삭제가 아니라 재분류**: 별도 액션 `system_status_change`(dry_run 관찰).
  사건 자체는 실재한다(예산 소진 = 볼륨을 남기고 멈춘 순간, D-NAO-59 목적함수의 관심사).
- 분류표는 **공식 스키마 enum**에 근거하되 **화이트리스트**로 짰다.

### 📌 교훈
1. **파생 값으로 원본을 역추론하기 전에, 원본이 응답에 있는지 먼저 본다.** 이 버그의 두 필드는
   모두 이미 응답에 있었고 공식 스키마에도 문서화돼 있었다. 비용은 fetcher 한 줄이었다.
2. **공식 문서의 enum을 닫힌 집합으로 믿지 마라.** 라이브 실측이 문서에 **없는 값 2종**을 보여줬다
   (`ELIGIBLE`, `BUSINESS_CHANNEL_ABNORMAL_INTERLOCK`). 그래서 분류는 "모르는 값"을 반드시 갖고,
   **모르면 사람 탓으로 돌리지 않는 방향**으로 실패해야 한다(유령을 만들지 않는 쪽).
3. **같은 개념을 계층마다 다르게 구현했으면 그 자체가 버그 신호다.** 그룹·키워드는 맞고 캠페인만
   틀렸다 — "왜 이 계층만 다르지?"를 물었으면 실측 없이도 잡혔다.
4. **오탐이 적다고 안전한 게 아니다.** 5건 중 1건뿐이었던 이유는 감지기가 아니라 크론 시각
   (07:35 KST)이 예산 소진 시각(저녁)과 안 겹쳤기 때문. **노출 창을 세지 말고 구조를 봐라** —
   저녁에 sync를 한 번 돌리자마자 바로 발생했다.
5. **오탐을 고치면 그 오탐이 DB에 남긴 값도 같이 치워라.** 잘못 기록된 `status='off'` 한 행을
   그냥 두면 다음 sync가 그걸 기준으로 **반대 방향 유령("외부 재개")**을 새로 만든다.

## 44. 면제 타입을 추가하면 "쓰기 경계"를 같이 열어야 하고, 면제를 잠그는 락도 같이 달아야 한다 (2026-07-27, CS 스프린트 PR #123)

### 🐛 이슈
콜드 소재 첫 입찰 타입 `bid_up_cold`를 만들면서 `BID_UP_TYPES`·`CHANGE_PCT_EXEMPT_TYPES`에만
등록했다. 결과는 정반대 실패 두 개가 **동시에**:
1. **아무것도 집행 안 됨(P1-1)** — `BID_UP_TYPES`에 넣는 순간 소재(ad) UP 쓰기 경계

   `dry_run=False`로 harness까지 태우는 테스트가 하나도 없었기 때문. dry-run만 테스트하면
   쓰기 경계의 모든 게이트가 실행되지 않는다.
2. **가장 약한 UP 경로가 됨(P1-3)** — ±15% **완전 면제**인데 그 면제를 잠그는 락이 하나도

   쌍방향 잠금이 fail-closed로 막는다.
추가로 "첫 1회만" 상태가 `rationale LIKE '[접두]%' AND dry_run=False`였는데, harness의
`_guard_failure`가 **제안 rationale을 그대로 앞에 붙여** 차단 행을 남기므로 **가드에 막힌 시도가
소재의 유일한 기회를 태웠다**(P1-2). 라운드 캡도 `executed`(성공) 기준이라 집행이 실패하면
캡이 영원히 안 걸렸다(P1-4).

### ✅ 해결
소재 UP 화이트리스트를 `(승인원 → 허용 타입)` 쌍방향 맵으로 바꿔 `cold_op ⟺ bid_up_cold`를
열고, 면제를 잠그는 **5중 락**을 달았다: ①타입⟺승인원 쌍방향 ②`target_type='ad'` 강제
③상한 마커(`encode/decode_cold_ceiling`) 쓰기-경계 재검증(탐색 `explore_ceiling` 동형·별도 태그)
④신선도 60분 ⑤위임 영구 제외 + 킬스위치 화이트리스트 2곳. "첫 1회" 판정은 텍스트 LIKE 대신
`proposal_id` 조인 + `after_value IS NOT NULL`(쓰기 확정)로, 라운드 캡은 시도 기준으로 교체.
`dry_run=False` 회귀 테스트 13종 추가(공격 재현 4종 포함).

### 📌 교훈
- **새 bid 타입을 레지스트리에 등록하는 것은 절반이다.** 나머지 절반은 (a) 그 타입이 지나갈
  **쓰기 경계**를 여는 것과 (b) 받은 **면제를 대신 잠그는 브레이크**를 다는 것이다. 이 코드베이스의
  기존 면제 타입은 **전부** 대체 브레이크를 갖고 있다(explore=상한 마커, servo/rank=base_bid
  TOCTOU+신선도). 선례를 먼저 읽고 그대로 따를 것.
- **dry-run만 테스트하면 쓰기 경계는 한 줄도 실행되지 않는다.** 실집행 경로(writer 스텁까지
  도달)를 타는 테스트가 없으면 "전건 차단"과 "전건 통과"를 똑같이 통과로 보고한다.
- **`_guard_failure`는 제안 rationale을 앞에 붙여 기록한다.** rationale 접두 매칭으로 상태를
  판정하면 "성공 1회"가 아니라 "시도 1회"가 된다. 상태 판정은 `proposal_id` 조인 +
  `after_value IS NOT NULL`(= 쓰기 확정)로 할 것.
- **캡·쿼터는 성공이 아니라 시도로 세라.** 실패가 카운터를 안 올리면 장애 시 캡이 사라진다.
- `created_at`은 `func.now()` = **UTC**다(기존 교훈 재확인). 신선도 게이트에서 KST `now`와 직접
  빼면 모든 행이 540분 늙은 것으로 보여 게이트가 전건을 죽인다 — `+9h` 보정 필수.
- **콜드 대상은 표본 기반 게이트에 구조적으로 걸린다.** 정착 표본이 없는 게 콜드의 정의인데
  BEP 완전성 게이트는 표본을 요구한다 → 탐색과 동일한 면제가 필요하고, 면제는 **타입 ∧ 승인원**을

## 51. DOMParser 문서의 innerText는 textContent다 — 셀 안 공백은 "코드가 만든 것"이 아니라 "남의 마크업 들여쓰기가 준 것" (2026-07-28, 로켓 1P M2)

### 🐛 이슈
페처 3종의 DOM 추출은 `td.innerText.trim().replace(/\s+/g,' ')`로 셀을 뽑았다. 렌더링된 문서라면 innerText가 요소 경계에서 줄바꿈을 넣어 준다 — 그런데 `new DOMParser().parseFromString(...)`으로 만든 문서는 **렌더링되지 않으므로 innerText가 textContent로 떨어지고, textContent는 요소 사이에 아무것도 넣지 않는다.** 즉 `<li>바코드</li><li>상품명</li>`은 `"바코드상품명"`이 된다. 지금 공백이 있었던 이유는 순전히 **쿠팡 SSR 마크업의 들여쓰기**(태그 사이 개행)였고, 쿠팡이 HTML을 미니파이하는 순간 사라진다. 터지는 자리는 `barcode, _, name = cell.partition(" ")` — 인덱스가 걸린 `barcode` 컬럼에 상품명이 들어가고 `product_name`이 None이 되는 **조용한 데이터 오염**(예외도 로그도 없음).

### ✅ 해결
자손 **텍스트노드**를 모아 명시적으로 `' '`로 조인하는 공용 헬퍼(`_CELL_HELPERS_JS`)로 두 추출기를 통일. 단 `<br>`은 분리자로 취급하지 않는다 — 헤더가 `상품<br>번호`·`세액<br>부가세`로 조립돼 있어서 공백을 넣으면 표 선택 토큰 매칭(`indexOf('상품번호')`)이 깨져 **rows=[] 무성 전손**이 된다. 파서 쪽 안전망은 "공백 유무"가 아니라 **"선두 토큰이 바코드꼴인가"**로 판정(상품명 자체에 공백이 있어 공백 유무로는 못 잡는다 — 첫 시도가 여기서 실패했다).

### 📌 교훈
- **남의 HTML에서 공백은 데이터가 아니다.** 셀 텍스트를 토큰으로 쪼개 쓸 거면 그 공백을 내 코드가 보장해야 한다. "지금 값이 맞게 나온다"는 상대의 포맷팅에 얹혀 있는 것일 수 있다.
- 파싱 계약을 바꿀 때는 **기록된 추출 출력(fixture/증거 파일)을 회귀 기준선으로 삼고 old·new를 같은 입력에 돌려 셀 단위로 대조**한다. 여기서는 `<br>` 취급이 그 대조 때문에 잡혔다.
- 공백 소실 방어는 **입력을 두 벌 만들어**(원본 / 태그 사이 공백 제거) 같은 출력이 나오는지 보면 된다 — "공백 독립성"이 검증 가능한 형태의 명제다.
- 브라우저가 필요한 검증은 백엔드 pytest에 넣지 말 것: `test_fetcher_button_only_chrome.py`가 playwright를 **sys.modules 스텁으로 막아** 단독 실행은 통과하고 전체 스위트에서만 실패하는 순서 의존 테스트가 된다(실제로 겪음). 실동작 증명은 `tools/verify_*.py` 스크립트로 내보내고 pytest에는 소스 가드(innerText 회귀 금지)만 남긴다.

## 53. 회계 의미가 grain마다 다른 값에는 "일괄 라벨"이 오히려 새 오류다 (2026-07-28, forecast pred_conv_amt 라벨 정정)

### 🐛 이슈
센티널 이중계산 조사(#128)의 후속 브리프는 명확했다 — "`pred_conv_amt`는 구매+장바구니 합이니 rationale 문구를 '전 전환액션 기준'으로 명시하라." 그대로 `_forecast_evidence_suffix`에 한 줄 붙이면 끝나는 일처럼 보였다.

그런데 그 함수는 **campaign / adgroup / keyword 세 grain의 제안이 전부 통과**하는 공용 경로였다. 소스인 `forecast_source.daily_series()`를 열어보니 센티널을 읽는 것은 **campaign 분기뿐**이고, adgroup/keyword는 상세 행이라 `conv_*`가 구매만이다. 브리프대로 일괄 라벨을 붙였다면 캠페인 표기는 고쳐지고 **키워드·그룹 표기가 새로 틀리는** 결과가 됐다 — 순수 구매 매출에 "구매+장바구니"라고 써 붙이는 셈.

### ✅ 해결
라벨을 grain별 매핑(`forecast_source.CONV_AMT_BASIS_LABEL`)으로 만들고, 소비처가 grain을 넘기게 했다(`_forecast_evidence_suffix(forecast, grain)`). 라벨의 단일 진실 소스는 **의미를 만들어내는 SA**(forecast_source)에 두었다 — 표시하는 쪽이 문구를 지어내면 소스가 바뀔 때 드리프트한다(원칙18-6). `SUPPORTED_GRAINS`↔라벨 키 집합 일치를 강제하는 드리프트 가드 테스트를 함께 넣었다.

또한 "라벨만 고치고 값은 두는" 판단의 근거를 코드로 확인했다: `_budget_proposal` 사이징은 `pred_cost`만 읽고, `response_curve_builder`는 `pred_conv_amt`를 **지역변수로 받아만 놓고 쓰지 않으며**, `flight_loop`의 rpc 집계는 이미 센티널을 제외한다. 즉 오염이 산식에 도달하지 않는다는 것을 확인한 뒤에야 "표시 문제"로 확정했다.

### 📌 교훈
- **"이 값이 뭘 뜻하나"를 고칠 때는 그 값이 흐르는 경로 전체의 grain/스코프를 먼저 나눠본다.** 공용 표시 함수 하나에 라벨을 박는 것은, 그 함수를 지나가는 모든 스코프가 같은 의미일 때만 옳다.
- **브리프가 정확해도 갈래는 안 적혀 있을 수 있다.** 이번 브리프는 campaign 분기만 보고 쓰였고 틀린 말은 하나도 없었지만, 그대로 실행했으면 반대 방향 오류를 새로 만들었다. 지시받은 파일을 열기 전에 **소비처를 grep으로 전수**하는 습관이 이 차이를 만들었다.
- **"표시만 고치고 계산은 둔다"는 결론에는 증거가 필요하다.** 소비처 전수(사이징·곡선·rpc·프론트)를 확인하지 않은 채 "rationale 병기용이니까 괜찮다"고 넘겼다면, 실제로는 산식에 물려 있었을 가능성을 안 본 것이다. **테스트 전량 무변경 통과**가 "값 불변"의 증거 역할을 한다 — 값을 바꾸는 안이었다면 forecast_scorer 테스트가 먼저 깨졌어야 한다.
- 부수 발견(별건): `response_curve_builder.build_response_curve`의 `pred_conv_amt` 지역변수는 **할당만 되고 미사용**이다. docstring은 입력으로 명시하고 있어 읽는 사람을 오도한다.

## 54. 파일 단위 배포의 의존 모듈 누락 → prod crash loop (2026-07-28, 프로모션 손익 페처 확장 배포)

### 🐛 이슈

## 55. 우회 사본은 원본 결함을 "고쳐진 것처럼" 보이게 만든다 — 구멍은 파생 규칙에서 메워라 (2026-07-28, EXECUTION_ACTIONS ↔ BP 라벨)

### 🐛 이슈
BP(예산 페이싱, D-NAO-102) 레인은 실행 경로가 `update_budget` 하나인데 change_log에는
`budget_up_pacing`/`budget_down_pacing`이라는 **다른 라벨**을 남긴다. `EXECUTION_ACTIONS`가
`_ACTION_BY_PROPOSAL_TYPE`의 값에서만 파생되어 그 라벨을 몰랐고, 그 결과 `/change-log?actor=ours`와
커맨드센터 1층 "우리 조작 N회"가 BP 실집행을 **한 건도 세지 못했다**. 0을 정직하게 말하려고 만든
필터가 정반대 방향으로 거짓말한 것(D-47-h 위반은 동일).

더 나쁜 건, 나중에 만들어진 성과 뷰 하니스가 `TODAY_ACTIONS = EXECUTION_ACTIONS | PACING_ACTIONS`로
**자기 자리에서만 우회**해 두었다는 점이다. 그 사본 때문에 "이미 처리된 문제"처럼 보였고,
원본 결함은 라우터에 그대로 남아 있었다.

### ✅ 해결
라우터에 같은 합집합을 하나 더 만들지 않고 **파생 규칙 자체**를 고쳤다
(`EXECUTION_ACTIONS = frozenset(_ACTION_BY_PROPOSAL_TYPE.values()) | frozenset(PACING_ACTIONS)`).
그 다음 성과 뷰의 우회 사본을 제거해 소비자가 보는 진실을 하나로 되돌렸다.
회귀 테스트는 목록을 다시 적는 대신 `_budget_log_action`을 **직접 호출**해 그 함수가 낼 수 있는
모든 라벨이 집합 안에 있는지 확인한다(사본을 만들면 그 사본이 다음 드리프트의 자리가 된다).
소비처 전수조사 결과 EXECUTION_ACTIONS 소비자는 라우터 2곳뿐이었고, 쿨다운(`compute_change_cadence`)은
action을 아예 안 보므로 가드레일에는 구멍이 없었다.

### 📌 교훈
1. **소비자가 자기 자리에서 합집합을 만들고 있으면 그건 우회지 수정이 아니다.** 사본을 발견하면
   원본 파생 규칙을 의심하라 — 사본 밖의 소비자는 여전히 구멍에 빠져 있다.
2. **"라벨만 분리한다"는 변경은 안전하지 않다.** 실행 경로가 그대로여도 그 라벨을 읽는 집합·화면·

## 56. git stash pop 누락으로 결정 기록이 은닉 유실된다 (2026-07-28, N1+03재가동+BP+VT3+성과뷰 세션)

### 🐛 이슈
같은 폴더에서 병행 세션의 반영을 위해 트랙 파일을 `git stash`한 뒤 `pop`하지 않고 계속 작업을 이어갔다.
그 결과 D-NAO-101~103(03 재가동·BP 예산증액·VT3 개편 결정)이 워킹트리에서 사라졌다 — 102·103은

없어져서 발견이 더 늦어짐). 기록 에이전트가 "해당 결정이 트랙에 없다"고 보고한 것을 교차 확인하는
과정에서 발견했고, `stash@{0}`에서 원문을 복구했다. (참고: 이번 세션에서 실제 복구를 시도해 보니
동일 내용이 병행 세션에 의해 이미 main에 별도로 커밋돼 있어 stash 자체는 결과적으로 중복이었다 —
그러나 stash가 없었다면 로컬에서 "결정이 사라졌다"는 잘못된 판단이 그대로 굳었을 위험은 동일했다.)

### ✅ 해결
`stash@{0}` 목록·diff를 먼저 확인해 잃어버린 결정 항목을 식별 → `git stash pop`으로 병합(3-way 충돌
발생, 삽입 위치가 겹치는 순수 순서 충돌이라 두 쪽 내용을 모두 보존하는 방식으로 해소) → 병합 결과가
이미 HEAD와 동일함을 `git diff HEAD`로 확인 → 안전하게 `git stash drop`.

### 📌 교훈
미커밋 문서(트랙 파일·계획서 등, 삭제 위험이 큰 "살아있는 기억" 파일)가 있는 상태에서 `git stash`를
쓸 때는 **같은 턴 안에 pop까지 마치거나, 아예 커밋해서 stash를 쓰지 않는다.** stash는 스코프 밖
변경을 잠깐 치우는 용도로만 쓰고, "나중에 pop"은 다음 세션·다음 sync에서 잊혀지는 게 기본값이라고
가정할 것. 원칙21(2-Layer 기억)의 Layer 1 파일은 stash 잔류가 곧 "기록 자체의 실종"이라 일반 코드
변경보다 훨씬 위험하다.

(19:49)과 소실 경위까지 함께 복원했다. 잘못된 지시가 남아 있던 244·598행도 정정.

### 📌 교훈
- **채번 전 `git log --oneline | grep D-NAO` 를 본다.** 트랙 파일은 "지금 파일에 남아 있는 것"만

- 병행 세션이 많은 날은 **덮어쓰기가 아니라 소실**이 일어난다. 문서 편집 전 `git log -3 -- <파일>`로
  최근에 누가 건드렸는지 확인하는 습관이 CAS(코드 배포)와 같은 역할을 한다.

## 64. 스위치의 존재를 기능의 존재로 착각하지 말 것 — "dry_run 해제가 위험하다"가 틀렸던 이유 (2026-07-28, 학습 배관 수리 2차)

### 🐛 이슈
이전 세션이 "`flight_loop`의 dry_run을 해제하면 68그룹짜리 인수 캠페인이 첫 실집행 대상이 되므로
위험하다"고 평가하고 보류를 권고했다. 근거는 그럴듯했다 — 예측 모델이 MAPE 50~180%로 강등된
이력이 있고 관측성도 없으니 신뢰도 낮은 예측이 실집행으로 흘러든다는 것.

**그런데 `flight_loop`에는 입찰을 바꾸는 코드가 아예 없다.** `naver_execution_harness`·
`naver_sa_writer` import 0건, 쓰기 호출 0건, 호출자는 스케줄러 1개뿐이고 기본값 그대로다.
docstring이 *"dry_run=False: α에 따른 입찰 변경 실행"*이라고 약속한 경로는 **구현된 적이 없다.**
해제해도 아무 일도 안 일어나고, change_log에 `dry_run=0`이라는 **거짓 라벨**만 붙는다.

즉 위험 평가와 그 반대편의 "해제하자"는 판단이 **둘 다 존재하지 않는 기능을 놓고 다투고 있었다.**

### ✅ 해결
`grep -rn "run_flight_loop"` 로 호출자 전수 + 모듈 내 쓰기 경로 전수 확인. "해제 보류"가 아니라
**"해제할 대상이 없다(연결된 게 없어서)"**로 결론을 바꾸고, 진짜 결정 사항은 "그 실행 경로를
만들 것인가"(Jino 판단)임을 명시했다.

### 📌 교훈
- **플래그를 평가하기 전에 그 플래그가 무엇에 연결돼 있는지 먼저 grep한다.** 파라미터 이름과
  docstring은 의도를 말하지 구현을 말하지 않는다 — [[naver-ad-claimed-vs-wired-gaps]]와 같은 계열.
- 위험 평가도 실측 대상이다. "위험하니 보류"는 안전해 보이지만, **틀린 근거 위의 보류는 다음
  세션이 같은 유령을 다시 평가하게 만든다**(실제로 이번이 두 번째였다).
- docstring이 미래형("~할 것이다", "Jino 전환 결정까지")으로 쓰여 있으면 그 경로는 **없을 가능성**을
  먼저 의심한다.

## 65. 두 쿼리가 같은 것을 세지 않으면 주석의 의도가 조용히 배신당한다 (2026-07-29, flight_loop 관측기+정착 스냅샷 필터 버그)

### 🐛 이슈
`conversion_maturity.take_daily_snapshot`의 docstring은 "아직 안 채워졌으면(미수집) 스킵한다"고
명시했다. 그런데 존재 판정(스킵 여부를 정하는 쿼리)은 `ad_date`만 걸어 백필 sentinel
(`__backfill__`) 행까지 "행이 있다"로 세고, 금액 집계 쿼리는 그 sentinel을 제외했다. 두 쿼리가
**서로 다른 모집단**을 본 것이다. 그 결과 "sentinel 행만 있는 ad_date"는 "행이 있다 → 스킵 안
함 → 금액 0"으로 흘러, docstring이 막으려던 바로 그 일("아직 안 채워짐"을 "진짜 전환 0원 확정"
으로 기록)이 그대로 일어났다. 07-01~03 코호트가 days_since 8~20에 0으로 박힌 뒤 계단형으로
점프하는 인위적 패턴이 됐고, `compute_curve`(코호트별 비율의 단순평균)가 이 오염된 코호트와
정상 코호트를 섞어 days 8~18에서 정확히 4/7=0.5714로 고정되는 곡선 퇴화를 만들었다 —
D-NAO-116·117에서 "원인 불명"으로 남겨뒀던 그 정체 구간의 정체였다.

### ✅ 해결
존재 판정 쿼리에도 금액 집계와 동일한 sentinel 제외 필터를 걸었다. 회귀 테스트 2건 추가
(필터를 되돌리면 실패함을 실증).

### 📌 교훈
- **같은 판단(스킵할지 말지)에 쓰이는 쿼리들은 같은 모집단을 보는지 대조하라.** 특히 한쪽에만
  예외 필터(sentinel 제외, 상태 필터 등)가 붙어 있으면 그 비대칭이 바로 버그의 자리다.
- docstring이 "이런 경우엔 스킵한다"고 명시할수록, 그 스킵 판정이 실제로 무엇을 세는지 별도로
  확인해야 한다 — 의도가 코드로 옮겨지는 과정에서 판정 쿼리와 실행 쿼리가 갈라지기 쉽다.

## 66. 타임스탬프 컬럼의 의미를 확인하기 전에 그것으로 판정 규칙을 만들지 말 것 (2026-07-29, 정착 스냅샷 필터 버그 조사 중)

### 🐛 이슈
위 #65를 고치는 과정에서 "과거에 이미 오염된 스냅샷 행을 어떻게 식별해 지울까"를 고민하다
`naver_ad_daily.synced_at`을 "그 행이 최초로 도착한 시각"으로 가정하고 "스냅샷 시각 <
MIN(synced_at) → 그 스냅샷은 무효"라는 삭제 규칙을 세웠다. 그런데 실제로는 `ad_daily_ingest`가
**매 수집마다 해당 날짜 데이터를 전량 delete-후-재삽입**하며 `synced_at`을 새로 찍는다 —
즉 "최초 도착 시각"이 아니라 "마지막 재수집 시각"이다. 이 규칙을 prod 사본에 실제로 적용해
보니 **정상 관측 203행(전체 420행의 48%)까지 무효로 판정**됐다. 실행 전에 발견해 폐기했다.

### ✅ 해결
규칙을 실행하기 전에 `ad_daily_ingest`의 upsert 로직을 직접 읽어 `synced_at`의 실제 의미를
확인했고, "최초 도착"이 아님을 확인한 즉시 그 규칙을 버렸다. 결론: 과거 오염 행은 사후 식별
수단이 없으므로 삭제하지 않고 그대로 둔다(#65 수정 이후 신규 코호트만 깨끗함이 보장됨).

### 📌 교훈
- **삭제·정정 규칙의 기준으로 삼을 타임스탬프 컬럼은, 그 컬럼을 쓰는(쓰는=기록하는) 코드를
  먼저 읽어 의미를 확정한 뒤에만 규칙에 쓴다.** 컬럼 이름(`synced_at`)이 암시하는 의미와 실제
  구현이 다를 수 있다.
- **upsert(delete-후-재삽입) 패턴의 테이블은 특히 위험하다** — "생성 시각"류 컬럼이 매 재수집
  마다 갱신되므로 이력 추적용으로 쓰면 안 된다.
- 이번엔 실행 전에 잡았지만, 다음엔 실행 후에 잡힐 수도 있다. **파괴적 규칙은 먼저 읽기전용
  으로 영향 범위(몇 %가 걸리는지)를 실측한 뒤 실행한다** — 원칙22(라이브 증거)와 같은 결.
