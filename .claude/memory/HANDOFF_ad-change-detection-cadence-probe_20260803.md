## §2 ★비용 전제가 틀렸다 — 24배가 아니라 0.5배

§11은 "광고그룹당 1콜 × 242"를 고정 비용으로 보고 "시간당 = 5,808콜(24배)"을 계산했다. 그 전제가 틀렸다.

공식 스웨거(`naver/searchad-apidoc` gh-pages `assets/json/ncc-heroes-ncc.json`)에 **`GET /ncc/ads{?ids}` — 소재 ID 목록 일괄 조회**가 있다.

**prod 라이브 실측:**

| | 현행(그룹별) | `ids=` 배치 |
|---|---|---|
| 전량 1,759소재 | **242콜 / 90.3초** | **5콜 / 5.48초** |
| 미반환 | — | **0건** |
| 반환 필드 | editTm·adAttr·userLock | 동일 **+ delFlag·nccQi·referenceData** |

- **배치 상한 실측**: 1→200→500 전부 HTTP 200(500건 1.80초) / **600·700·800·1000 → HTTP 414**. 414는 nginx `Request-URI Too Large`이지 **API 한계가 아니다**(id 평균 27자). → 안전값 **400**.
- **시간당으로 올려도 하루 120콜 = 현행 242콜의 절반.** 미확인 rate limit 리스크가 오히려 **줄어드는** 방향이다.
- **한계**: `ids=`는 **우리가 아는 소재만** 본다. 신규 소재 발견은 그룹별 스윕이 계속 필요하다. 자연스러운 형태는 "일 1회 그룹 스윕 = 발견 + 고빈도 `ids=` 스윕 = 탐지" 분리지만 **이건 설계안이지 결정이 아니다.**

**rate limit은 여전히 문서 미확인.** 공식 스웨거·`NaverSA_API_Error_Code_MAP.md` 전문 확인 결과 수치 규정 없음. 존재 증거는 에러코드 **1014**(최대 허용개수 초과)·**1016**(너무 많은 접속)뿐. **추정하지 않는다.**

기각한 후보: `/ncc/inspect-history`(스웨거 `ncc-inspect-history.json`) — 이름과 달리 **검수(광고 심사) 이력**이지 변경 이력이 아니다.

## §3 ★★`ad_edit`의 정체 — 네이버의 상품 피드 재적용이지 대행사 조작이 아니다

12:09 기준선 대비 라이브를 읽기 전용으로 대조한 결과: **editTm 전진 233건 · 우리 쓰기 0건**(오늘 우리 `change_log`는 `flight_pacing` dry_run=1 뿐).

같은 소재의 **과거 전체 스냅샷**(`naver_change_log.after_value`에 저장된 `get_ad` 원본, 대조 가능 18건)과 필드 단위로 대조하니 바뀐 것은 **`referenceData` 하위의 상품 데이터뿐**이었다:

**광고 설정(`adAttr.bidAmt`·`useGroupBidAmt`·`userLock`)은 한 건도 안 바뀌었다.** 즉 스마트스토어 상품 데이터가 갱신되면 네이버가 쇼핑 소재를 재적용하고, 그 부수효과로 `editTm`이 전진한다.
