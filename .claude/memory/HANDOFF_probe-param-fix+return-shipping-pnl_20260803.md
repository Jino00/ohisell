## §1 프로브 파라미터 정정 (PR #181)

07-31 배포본이 라이브에서 전손했다 — `fetch_case_settlement_by_order`가 `orderId`에
`periodType`·`settleDecisionType`을 함께 실어 매 호출 400을 받았고, 호출부가
`(r or {}).get('elements', [])`로 읽어 그 400을 "정산 행 없음"으로 오독했다.

```
orderId + periodType     → 400 "periodType 값은 orderId, productOrderId 값과 같이 입력될 수 없습니다"
orderId + searchDate     → 400 (같은 문구)
orderId 단독(+page/size) → 200
```

**추가 발견**: `settleDecisionType`은 **응답 스키마에 아예 없는 필드**다(공식 스펙 확인). 요청
필터일 뿐인데 저장 테이블의 관측 축이자 UNIQUE 키였다. 축을 응답에 실제로 있는 `settleType`으로
옮기고 컬럼을 삭제했다(마이그 `e7b2c9d4a610`).

**라이브 합격**: 주문 33건·관측 62행·신규조합 8건. N배송 반품 2건이 각 2행
(`PROD_ORDER`/`DELIVERY` 모두 `NORMAL_SETTLE_BEFORE_CANCEL`) — Jino가 못 박은 합격 조건 그대로.
재실행 멱등(적재 0·발송 생략) 확인 후 `is_enabled=1` + 재시작, 잡 등록 로그 확인.

★병행 세션(PR #180)이 같은 alembic 갈래를 **다른 방법**(자기 리비전 재부모)으로 고쳤는데
내 합류 리비전과 겹치고도 단일 head로 수렴했다 — 운이었다(LESSONS #84).

## §2 반품 배송 손익 배선 (PR #184) — 이번 세션의 본체

**결함**: 반품 건은 `REVENUE_EXCLUDED`라 매출·원가뿐 아니라 **출고비·회수비·반품비 수입이 전부
0**이었다. 대시보드에서 반품은 공짜였고, 반품률이 올라도 이익이 반응하지 않았다.

### 원천 실측 (반품 86건 전수, `raw_data.return.*`)

| 배송 | 고객 청구 | 네이버 지원 | 회수사 | 건수 |
|---|---:|---:|---|---:|
| N배송 | 0 | **5,500** (`MEMBERSHIP_ARRIVAL_GUARANTEE`) | HANJIN | 2 |
| 일반 | 5,000 | 0 | HANJIN | 58 |
| 일반 | 0 *(미청구)* | 0 | HANJIN | 20 |
| 일반 | 2,500 / 7,500 | 0 | HANJIN | 4 / 2 |

- **정액 폴백 금지** — 미청구 22건이 +5,000 수입으로 잡혀 반품이 이익 나는 일이 된다.
  수입은 `claimDeliveryFeeDemandAmount` **건별 실측**만 쓴다.
- **회수는 N배송 포함 전부 한진**(출고는 품고여도 회수는 아니다). 그래서 회수비 단가 축은
  배송방식이 아니라 **회수 택배사**다.
- **네이버 지원액을 반드시 함께 본다** — N배송 반품의 고객 청구 0은 우리 손실이 아니라
  네이버가 5,500원을 내기 때문이다. 청구액만 보면 부호가 반대로 읽힌다(LESSONS #95).
  회수비를 지원액만큼 상계하되 **상한 = 회수비**. 초과분 3,000원은 실제 지급 여부가 정산에서
  미확인이라 수입으로 잡지 않는다 → **프로브가 08-06·08-09에 잡으면 재심**.

### 설계

- 컬럼 4개(마이그 `a2d5f80c34b7` + `b6e1c93f4275`): `return_completed_at` /
  `return_fee_demand_amount` / `return_collect_company` / `return_fee_support_amount`.
  **NULL=반품 아님, 0=미청구(실측된 0)** — 둘을 구분한다.
- **귀속일 = 반품 완료일**(Jino: "과거 이익이 흔들리면 안 돼"). `returnCompletedDate` 86/86 커버리지.
- 수입은 기존 배송수입과 **똑같이** 처리(수수료 포함, `order_count`는 안 올림) — 정산 원장이
  원 배송비와 반품비를 구분하지 않고 같은 `DELIVERY` 행에 같은 수수료를 매기기 때문
  (5,000→136 · 3,000→81, 2.724% 절사).
- **상품별 이익에도 반영**. 처음엔 "배분 규칙이 없다"고 뺐는데 반품 86패키지가 전부 상품
  1종이라 배분할 게 없었다(Jino 지적, LESSONS #87).
- 백필: `scripts/backfill_order_return_fields.py` (라이브 110행).
