## 2. 판단기준

1. **항상 엑셀이 정본이다 — 컷오버 선언 전까지.** 왜냐하면 정본이 둘이 되는 순간이 71건 역전
   사고의 재판이기 때문이다. 시스템 계산값이 정본과 다르면 고칠 것은 시스템이다.
2. **값은 항상 Jino 확인분만 넣는다.** 왜냐하면 추론 동일시가 08-10 사고 그 자체다(교훈 #204).
3. **재계산은 항상 쓰기 시점이다.** 왜냐하면 소비처 14+곳이 SQL 조인으로
   `product_master.cost_price` 스칼라를 직접 읽고, `NaverProductBep`가 매일 그 값을 스냅샷으로
   복사한다 — 읽기 시점 계산은 이들에게 보이지 않는다.
4. **미입력은 항상 «구성 없음»으로 표현한다, 0으로 채우지 않는다.** 왜냐하면 0=미입력 혼동이
   이 스키마의 기존 결함이고, 새 층에서 재생산하면 만들 이유가 없다.
5. **산술은 항상 한 벌 — 순수 SA로 두고 임포트한다.** 왜냐하면 사본 두 벌은 «감시자가 감시
   대상보다 낡는» 형태다(ref 54 §9 실증).
6. **「됐다」는 항상 라이브 경로 증거로만.** 격리 테스트 통과는 필요조건일 뿐이다 — 검사기
   배선 때 배선 테스트 6건이 하나도 안 죽었던 전례(ref 54 §9 P1-1).

## 3. 금지선

- **`cost_price` 컬럼을 지우거나 의미를 바꾸지 않는다.** 소비처는 한 곳도 건드리지 않는다(§5).
- **정본 스냅샷 검사기(`cost_truth_audit.py` · `cost_truth_20260807.json`)를 무장해제하거나,
  판정을 맞추려고 스냅샷을 수정하지 않는다.** 검사기가 울면 시스템 쪽을 고친다.
  스냅샷 교체는 컷오버 절차(§6)에서만.
- **`models.py`를 마이그레이션보다 먼저 배포하지 않는다.** `safe_deploy.sh --migrate` 순서 강제
  — 이 앱은 부팅 시 마이그를 돌지 않는다.
- **구성이 등록된 SKU의 `cost_price`를 스칼라 업로드 3경로가 덮어쓰게 두지 않는다**
  (`POST /api/products/upload` · `/upload-by-name` · `PUT /api/products/{id}`).
  옛 엑셀 v3 업로드 = 버퍼 177건 복귀 시나리오를 경로 차원에서 차단.
  구성 미등록 SKU는 종전대로 동작한다(하위호환).
- **`known_buffers`를 구성층의 정식 항목으로 되살리지 않는다** — D-CPP-34로 «단순 오류» 확정.
- **Jino 확인 없는 값·구성의 prod 반영 금지.** dry-run 결과 제시 → 승인 → 반영.
- D-CPP·교훈 번호는 `scripts/next_ids.sh`로만 받는다(병행 세션 충돌).
- PR 경계 적대 리뷰 1회 없이 slice를 닫지 않는다 — DB 스키마 변경이라 면제 없음.
  재현 요구 + 변이 주입 포함.

## 4. 합격기준 — 라이브 증거 시나리오

「테스트 통과」·「코드 존재」는 합격이 아니다. 아래가 **prod에서 관측**되어야 slice 1 합격이다.

1. **무해성**: 마이그 적용 + 코드 배포 직후 `GET /api/scheduler/health`의 `cost_drift`가 배포 전과
   동일하고(현재 0건), 손익 API 2곳(profit_calculator 경유 1 + 로켓1P 1)의 원가 합계가 배포 전
   캡처와 일치한다. **구성층이 얹혔을 뿐 아무 값도 안 움직였다**는 증거.
2. **계산 정합**: 일반 폰 대표 SKU(지문방지필름 TPU 3매)에 부자재 구성 9종을 입력하면 시스템
   재계산값이 **prod API 응답에서 2,350.7**로 관측된다(정본과 소수 1자리 일치). `cost_drift` 0건 유지.
3. **전파**: 공통 부자재 단가 1건을 바꾸는 API 호출 한 번에 그 부자재를 참조하는 **전 SKU의
   `cost_price`가 같은 트랜잭션에서 갱신**되고, 영향 건수·before/after 이력이 API로 조회된다.
   원복까지 왕복 재현하고 `cost_drift` 0건 복귀 확인.
4. **덮어쓰기 차단**: 구성 등록 SKU가 포함된 옛 형식 엑셀을 업로드하면 해당 SKU는 **건너뛰고
   그 사실이 응답에 보인다** — v3 재업로드 사고의 재현 불가 증거.
5. 대조 상태 악화 없음: `ok ≥ 490`, `buffered = 0`.

## 5. 마이그레이션 전략 (권고)

**권고: `cost_price`를 유지하고 «구성 합계의 캐시»로 격하한다.** 새 테이블 3개 —
부자재 마스터(단가) · 공통 입력(환율·관세율·부가세율 등 이름 있는 스칼라) ·
SKU별 구성(부자재/공통입력 참조 × 수량, 계산식 종류 태그: 단순합 vs CNY 환산).
쓰기 시점(구성 변경·공통 입력 변경)에 순수 SA가 합계를 계산해 `cost_price`에 기록하고 이력을 남긴다.

**근거**: 소비처 14+파일이 **SQL 조인으로 스칼라를 직접 읽는다**는 사실이 결정한다. 전부
갈아타기는 폭발 반경이 손익 엔진 전체 + 매일 도는 `NaverProductBep` 스냅샷이고, 회귀 검증면이
이 작업 본체보다 커진다. 캐시 방식이면 소비처는 배포 당일 아무것도 모른 채 종전과 같은 숫자를
읽고, 정합은 기존 `cost_drift` 검사기가 그대로 감시한다 — **이미 사는 감시 장치를 안전망으로
재사용하는 유일한 선택지**다.
*(대안: 뷰/조인 전환으로 스칼라를 없애는 안 — 소비처 14곳 전면 회귀 + 스냅샷 테이블 재설계가
필요해 기각.)*

**캐시 일관성**은 새 검사를 하나 얹는다: «구성 합계 ≠ `cost_price`인 SKU 수»를
`scheduler_health`에 `cost_cache_drift`로 추가(기존 `cost_drift` 패턴 그대로, fail-soft, 순수 SA 한 벌).
★헬스 응답에 뭘 추가하든 **넷을 짝지어야 한다**: ①`build_health`의 `healthy` 판정 ②반환 dict
③`schemas.py`의 `SchedulerHealthOut` ④`Layout.tsx` 배너 분기 + 프론트 타입.
테스트는 **HTTP body를 단언**해야 한다(ref 54 §9 P1-1 — dict까지만 보면 못 본다).

**공통 입력의 자리와 전파**: 환율·필름 단가 같은 공통 입력은 행 하나짜리 정규 데이터다.
변경은 전용 API로만 하고 그 트랜잭션 안에서 참조 SKU 전체를 재계산한다(쓰기 시점 — 판단기준 3).
읽기 시점 계산은 채택하지 않는다.

## 6. 엑셀과의 관계 — 단계적 이중 운영 후 컷오버

Slice 1~3 동안 **엑셀이 정본이고 시스템은 «재계산기»**다: 구성을 입력할 때마다 시스템 계산값이
정본 스냅샷과 일치하는지가 곧 검증이다(합격기준 2가 그 형태).

전 계열 이식이 끝나고 949행 기준 `buffered=0` · 판정가능분 전건 `ok`가 관측되면
**Jino의 명시적 선언으로 컷오버**한다(D-CPP-34에서 사전 동의 확보). 이후 원가 변경은 시스템에서만
하고, 스냅샷 검사기의 정본은 **시스템이 생성한 새 스냅샷**으로 교체된다 — 검사 방향이
«DB가 엑셀과 같나»에서 «캐시가 구성 합계와 같나»(`cost_cache_drift`)로 넘어간다.
**컷오버 전에 스냅샷을 건드리는 것은 금지선이다**(§3).
