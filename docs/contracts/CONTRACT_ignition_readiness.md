## 이 계약이 하는 일 / 안 하는 일 / 왜 자동 진행이 안전한가 (3줄)

- **하는 일**: 2026-08-26 세션이 확정한 결손 13개 중 **코드·DB로 채울 수 있는 11개**를 의존 순서대로 6개 슬라이스로 잘라, 착수하는 세션(들)이 **묻지 않고** 구현→리뷰→배포까지 완주한다. 끝나면 시스템은 「점화 결정만 나면 도는」 준비 완료 상태가 된다.
- **안 하는 일**: 점화(#1)·소유권 분리(#2)·의미단위 콘솔 실증(#7) — 상대(Jino 손·대행사)가 있는 셋은 이 계약 밖이다. **광고 계정에는 아무것도 쓰지 않는다.**
- **왜 안전한가**: 전 캠페인 `auto_operate=0`이고 이 계약은 그 값을 만지지 않는다. 신설 코드는 전부 판정·적재·표면층이며, 광고계정 쓰기 API 호출 0을 diff로 증명한다. **이 계약을 승인해도, 그리고 진행해도, 돈이 나갈 경로가 구조적으로 없다**(§3에서 경로별 증명).

## 2. 판단기준

1. **항상 광고 계정을 만지지 않는다**, 왜냐하면 자동 진행의 유일한 정당성이 「돈이 나갈 경로 없음」이고, 이 계약의 모든 산출물은 점화 «후»를 위한 준비이기 때문이다.
2. **항상 슬라이스 단위로 독립 완결한다**(구현→테스트→리뷰→배포→표면 확인을 슬라이스마다), 왜냐하면 이 트랙의 세션당 실적은 1~3슬라이스이고, 한 덩어리로 가면 첫 장애가 전체를 물귀신처럼 끌고 내려가기 때문이다.
3. **항상 기존 숫자를 재사용하고 새 상수를 발명하지 않는다**(등급 만료 30·90일 = 재심사 백오프 기존값, SPECS 봉투 끝값 = 현행 게이트·산업 표준 21클릭 등), 왜냐하면 근거 없는 상수는 다음 감사가 들추는 부채이기 때문이다.
4. **항상 실측이 전제를 반증하면 §4-B ④를 따른다**, 왜냐하면 2026-08-26 하루에만 전제 반증이 세 번 났고(70/70 「15그룹」→라이브 5그룹 등), 반증을 삼키면 계약이 거짓 위에 선다.
5. **항상 대행사 칸에는 라벨만 붙이고 실행하지 않는다**(백필 = 우리 DB 원장의 컬럼 갱신, 광고계정 무접촉), 왜냐하면 남의 조치를 되돌리는 것은 소유권 분리 전 금지선이기 때문이다(ref 66 §5-3).
6. **항상 Jino가 명령 한 줄로 확인할 수 있는 표면을 슬라이스마다 남긴다**, 왜냐하면 자동 진행의 신뢰는 보고가 아니라 관측 가능성에서 오기 때문이다.

## 3. 금지선 — 「돈이 나갈 경로가 없다」의 증명

- **광고계정 쓰기 API 호출 0.** `naver_sa_writer`의 쓰기 함수 호출 경로를 신설하지 않는다 — 각 슬라이스 PR에서 diff로 증명(리뷰 검사 항목).
- **`auto_operate`·`optimizer` 값 변경 0.** 현재 전 캠페인 0/none([I])이 실집행의 유일 게이트이고, 이 계약의 어떤 코드도 그 값을 쓰지 않는다. S6의 «관할 등록»조차 `auto_operate=0`으로만 행을 만든다.
- **DB 스키마는 마이그레이션으로만** + `scripts/safe_deploy.sh --migrate` 순서(마이그→upgrade→코드→재시작). 신설 컬럼은 전부 additive nullable — 구코드가 새 스키마 위에서 그대로 돈다.
- **마이그 실패 시 수동 downgrade 금지**(§4-B ②의 처분을 따른다 — 순서 규칙상 실패 시점의 prod는 구스키마+구코드로 무결).
- **재개방(`_open_exclusion`)·제외 발사·probation 전이의 «실행» 0건** — S3는 배선까지이고, 실행 게이트(`auto_operate`)는 닫혀 있다.
- 백필은 `console_import` 행의 **라벨 컬럼만** 갱신 — `restrict_kwd_id`·라이브 상태에 무접촉.
- force-push 금지 · `git add -A` 금지(경로 지정 커밋) · 시크릿 파일 무접촉 · 네이버 API는 **읽기(GET)만**, 그것도 S5 수집 경로에 한정.
- 「전수 완료」·「준비 완료 = 성과 보장」이라 쓰지 않는다.

### 4-B. 자동 판단 규칙 — 갈림길마다 미리 내려 둔 답

**① 적대 리뷰가 P1을 내면**: 그 슬라이스의 diff 안에서 고칠 수 있으면 같은 세션에서 수정→2R(수정 diff만). 2R에서 **새** P1이 나오거나 수정이 슬라이스 경계를 넘으면 → 그 슬라이스는 **머지 없이 닫고**(반착지 — PR은 남긴다) 부채 기록 후 다음 슬라이스로. P1=0만이 머지 조건이다.

**② 마이그레이션이 prod에서 실패하면**: 중단이다 — 롤백 시도 금지. `--migrate` 순서 규칙상 실패 시점의 prod는 구스키마+구코드로 무결하므로 **아무것도 되돌릴 필요가 없다.** 실패 로그·재개 명령을 기록하고 마이그 없는 슬라이스(S1·S3·S6 일부)로 넘어간다.

**③ 예산 소진 시**: 새 슬라이스를 시작하지 않는다. 진행 중 슬라이스는 최소 «커밋→PR»까지 착지시키고, HANDOFF에 잔여 슬라이스와 이 계약 좌표를 실어 다음 세션이 이어받는다. **반쯤 배포된 상태로 세션을 닫는 것이 유일한 금지 — 배포는 슬라이스 완결 시에만.**

**④ 실측이 계약의 전제를 반증하면**(2026-08-26에 세 번 있었다): ⓐ반증을 증거 좌표와 함께 먼저 기록 ⓑ슬라이스의 목표가 유지되면 구현만 사실에 맞춰 조정(합격기준 원문은 안 고친다 — 무의미해진 항목은 「전제 반증 — 판정불능」으로 남긴다) ⓒ슬라이스의 존재 이유가 죽으면 그 슬라이스를 건너뛰고 기록 ⓓ**계약 전체의 목적이 흔들리면 멈추고 Jino에게 남긴다** — 그건 목적 전환이 아니라 새 계약 영역이다(전역 §2).
