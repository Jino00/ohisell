## §2. 판단기준

- **항상 실행 결정권은 백엔드 게이트에 두고 Mac 페처는 실행기로만 쓴다**, 왜냐하면 supplier는 Akamai 뒤라 통로가 Mac 헤드풀 Chrome뿐인데(`CONTRACT_1p_invoice_gap.md` 부록 A-5), 실행기가 판단까지 가지면 거부·감사 로그가 두 런타임으로 갈라지고 Mac 사본은 저장소와 어긋난 채 돌 수 있다(교훈 #371 — 머지 ≠ Mac 배포). 게이트는 `_write_guard.py:26-83` `guarded_write` 패턴 그대로: dry_run 기본(`:33`) + `CONFIRM_LIVE_WRITE` 토큰(`:15`, 검증 `:69-74`) + 라이브 시 WARNING 감사 로그(`:76`). 페처는 **DB에 존재하는 명령만** 실행한다 — 명령을 발명하지 못한다.
- **항상 한 명령 = PO 1건 = POST 최대 1회다**, 왜냐하면 실패 응답이 비구조화라(`alert(data)`, ref 106 §3) 배치의 부분 실패를 응답만으로 못 가르고, 성공/실패의 단위를 PO 1건으로 잘라야 감사 레코드 1행 = 사실 1개가 된다.
- **항상 POST 직전에 그 발주상세를 GET해 `id="btnConfirmInvoice"` 존재를 실측하고, 없으면 POST 없이 「이미 처리됨」으로 종료한다**, 왜냐하면 버튼 렌더가 서버측 상태 게이트임이 실측됐고(RI 3/3 존재 · CI·PA·RP 0/3 — ref 106 §2), 「버튼 존재 = 지금 확인 가능」이 정본이다. 이 사전 게이트가 멱등성 `[미상]`을 실험 없이 우회하는 유일한 수단이다 — 우리 원장의 RI는 **후보 목록**일 뿐 실행 근거가 아니다(원장은 마지막 수집 시점의 상태라 굳을 수 있다 — 2026-08-27 실사고: RI 12건 중 8건이 8/5에 굳어 있었다).
- **항상 자동 재시도를 하지 않는다 — 결과를 모르면 「결과 미상」으로 표면화하고 멈춘다**, 왜냐하면 이미 확인된 건에 같은 POST를 보내면 어떻게 되는지 모르고(`[미상]`, 호출 전례 0건), `refresh_contract.py`의 lease 재시도는 읽기용 설계다(`:18` 실패 시 lease 반납 → 자동 재claim, `:386` — 쓰기에 얹으면 같은 확인을 두 번 누른다). 다음 시도도 반드시 사람 클릭에서만 시작하고, 그 시도조차 사전 GET 게이트를 다시 통과한다.
- **항상 실행 전·중·후의 관측 원문(사전 GET 판정 · POST 응답 body · 사후 재수집 상태)을 DB 감사 레코드에 남긴다**, 왜냐하면 RI로 되돌리는 경로가 화면에 없어(ref 106 §6 미상 3) **되돌릴 수 없다고 가정**해야 하고, 정정 경로가 없는 액션은 사후 가시성·근거 보존이 그 자리를 대신하는 전부다(전역 §1).
- **항상 결과는 Jino가 누른 그 화면에 돌아온다**, 왜냐하면 표면을 안 적으면 「만드는 데까지」에서 합격이 나고 닿는 구간은 아무도 안 본다(전역 §2 표면 규칙) — 로그에만 남는 실행 결과는 이 계약에선 실패 모드다.

## §3. 금지선

- **supplier 쓰기는 `POST /scm/purchase/order/confirmInvoice` 단 하나** — 다른 어떤 supplier 상태 변경 요청도 이 계약의 코드에서 전송 금지(회송지 수정·업로드 폼 포함).
- **자동 재시도 절대 금지** — 층 불문: 백엔드 재큐잉 금지 · 페처 루프 재실행 금지 · 프론트 자동 재호출 금지. `refresh_contract.py`의 lease 계약(실패 시 반납→재claim, 3회 예산)을 이 쓰기 채널에 재사용 금지. 명령의 임대는 **1회뿐**이고, TTL이 지나면 재임대가 아니라 「결과 미상」으로 종결한다.
- **사전 GET(버튼 존재 실측) 없이 POST 전송 금지.**
- **배치 전송 금지** — 한 명령에 PO 여러 건을 싣는 API·화면·페처 경로를 만들지 않는다.
- **사람 클릭 없이 명령 생성 금지** — 크론·수집 루프·자동화가 이 명령을 만드는 경로 금지. 명령의 유일한 생성점은 SellC 모달의 「실행」 클릭이다.
- dry_run 기본 + `CONFIRM_LIVE_WRITE` 토큰 없이 라이브 명령 생성 금지(`_write_guard` 패턴 — 토큰은 프론트가 「실행」 클릭 시에만 싣는다).
- **응답 원문 보존 없이 완료 처리 금지** — `data.success`만 남기고 body를 버리는 코드 금지(실패 시 body가 유일한 진단 재료다).
- prod 서버 IP로 supplier.coupang.com 호출 금지(선행 계약 상속 — api-gateway 수집까지 차단당한다).
- 배포는 `scripts/safe_deploy.sh`만(DB 변경 시 `--migrate` 순서 강제) · 병합은 `scripts/safe_merge.sh` · `git add -A`/`-a` 금지(경로 지정 커밋). Mac 페처 배포는 `tools/install_local_runtime.sh`(CAS·매니페스트)로만 — 머지 ≠ 배포(교훈 #371).
