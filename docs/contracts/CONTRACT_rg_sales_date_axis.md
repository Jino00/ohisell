## 2. 판단기준 (항상 A, 왜냐하면 ○○)

1. **항상 «그날 판 것»에 «그것에 붙는 비용»을 붙인다** — 왜냐하면 Jino가 보려는 것이 그것이고,
   기간 통짜는 그 기간의 어느 하루도 설명하지 못한다(08-18은 매출의 **625%**를 뺐다).
2. **항상 못 덮는 부분은 「모름」으로 말한다 — 0으로도, 통짜로도 채우지 않는다** — 왜냐하면
   0으로 채우면 순이익이 부풀고 통짜로 채우면 부호가 뒤집힌다. **둘 다 조용히 틀린다.**
3. **항상 요율·단가의 출처를 행에 싣는다** — 왜냐하면 실측값과 기본값이 같은 얼굴을 하면
   화면이 거짓 확신을 준다. 3P가 이미 `basis="default_rate"`로 이렇게 한다(`option_fee_rate.py:97`).
4. **항상 장부 총액을 보존한다** — 일별로 쪼개도 **창 합계가 실제 청구와 맞아야 한다.**
   왜냐하면 안 맞으면 「날짜별로 예뻐졌는데 총액이 틀린」 상태가 되고, 그건 지금보다 나쁘다.
5. **항상 3P의 기존 구조를 먼저 읽고 차용한다** — 왜냐하면 요율 캐시·폴백·basis 표시가
   라이브에서 검증돼 있고(정산 실측 661건 전수), 새로 만들면 같은 함정을 다시 밟는다.
   ★단 **RG는 「매출×요율」이 아니라 「수량×정액」이 섞인 구조**다(물류비는 개당 정액,
   판매수수료만 요율) — 패턴은 베끼되 식은 베끼지 않는다.
6. **원가 커버리지 게이트는 유지한다** — 왜냐하면 이건 2P가 3P·네이버보다 **나은** 유일한
   항목이고(그 둘은 원가를 몰라도 순이익을 그냥 낸다), 「3P와 같게」를 이유로 없애면 후퇴다.
7. **판정은 화면에서 한다** — 왜냐하면 「값이 계산된다」로 합격을 내면 사람에게 닿는 마지막
   칸이 검사되지 않는다(§2 ★, 전역 하네스).

## 3. 금지선

- **추정으로 채우고 자백 없이 순이익을 «단정»하지 않는다.** 요율·단가가 없으면 `basis`를 실어 보낸다.
- **원가 커버리지 게이트를 낮추거나 없애지 않는다.**
- **3P·네이버·로켓1P의 계산을 건드리지 않는다.** 공용 함수를 고쳐야 하면 그 자체가 설계 재검토 신호다.
- **정산 원장·판매 원장을 «쓰지» 않는다.** 이번 작업은 읽기만 한다(수집 개선은 범위 밖).
- **prod 배포는 `scripts/safe_deploy.sh`로만.** 직접 scp/rsync 금지(D-NAO-49). DB 변경 있으면 `--migrate`.
- **PR 병합은 `scripts/safe_merge.sh`로만.** CI가 결제정지로 빨간불이면 **서명을 직접 확인**하고 `--force`+자백.
- **트랙 목표를 이 계약 밖에서 바꾸지 않는다.** 바꾸려면 새 계약이다.

### 8-2. ★설계를 베낄 곳은 3P가 아니라 `product_pnl`이다

`product_pnl.py:349-375`가 **이미** 다음을 한다:
- 옵션 단위 정산 수수료를 읽는다 — `_agg_rg_settlement_fees(..., grain="option")`
- **VAT gross-up ×1.1**(`_RG_VAT_GROSSUP`) — 옵션 row는 **VAT前(A−B)**, 계정 row는 **VAT後**
- 잔차를 **두 이름으로 분리**한다(단일 plug 금지 — 「×1.1 오류·과귀속을 숨긴다」):
  - `rg_account_only_fees` = 옵션 row가 아예 없는 fee_type의 계정 VAT後 총액(정상 귀속불가분)
  - `rg_vat_grossup_gap` = 옵션 row가 있는 fee_type의 (계정VAT後 − Σ옵션×1.1). 정상 ≈0
- **보존식이 정확히 성립**한다: `Σ(옵션귀속) + rg_unmapped + rg_account_only_fees + rg_vat_grossup_gap == rg_total`

⇒ **계약 §4 ⓒ(장부 총액 보존)의 설계가 이미 존재한다.** 이번에 새로 만들 것은 **날짜 배분 한 겹**뿐이다 — `product_pnl`은 창 단위이지 일별이 아니다.
⇒ 따라서 §2 판단기준 5의 「3P 구조 차용」은 **판매수수료 요율 부분에만** 적용된다. 물류비는 `product_pnl` 패턴이다.

### 8-3. VAT 질문 부분 해소

코드가 명시한다 — **옵션 row = VAT前 · 계정 row = VAT後**(`intelligence.py:606-612`, `models.py` §8-1).
⇒ 부록 A-4 ①에서 역산한 `sale_fee` 요율 **8.42~10.23%는 VAT 포함 값**이고, ÷1.1 하면 **7.65~9.30%**가 VAT前이다.
★요율 «흔들림»(1.8%p)의 원인은 이것과 별개다 — S1에서 계속 규명 중(정산 인식 지연 / 카테고리 믹스 / `CoupangRevenueFee`에 RG 옵션 요율이 실재하는지).

### 8-4. 판매수수료 요율 — 네 가설 중 둘이 배제됐다 (§7-1의 답)

| 가설 | 판정 | 근거(실측) |
|---|---|---|
| **(a) 옵션별 실측 요율이 이미 있다** (3P의 `coupang_revenue_fee`) | **배제** | RG 판매 옵션(RFM)과 그 테이블의 겹침 **0건**(WING1·WING2 둘 다). 조인 자체는 정상 — 3P 대조군은 384건·266건 겹친다. **`coupang_revenue_fee`는 3P 전용이다.** ⇒ 요율 추정을 피할 경로가 없다 |
| **(b) 정산 인식 지연** | **배제** | 창을 1주 뒤로 밀면 편차가 **26배 커진다**(표준편차 0.699%p → **18.10%p**, 최대−최소 1.81%p → 48.59%p). 정반대 방향이다 |
| **(c) 카테고리 믹스 변화** | **배제 안 됨** (사실 확인, 인과 미확인) | 요율이 낮던 두 주기(8.42%·8.90%)는 **아이폰 강화유리 액정보호필름**이 상위를 지배했고, 오른 뒤 주기들은 **골프필름·Z플립/폴드 사생활필름**으로 완전히 갈렸다. 상위 5옵션 집중도도 63.5% → 82.1%로 상승. ★옵션별 실제 요율이 없으므로(위 a) **시점이 겹친다는 사실만** 확정 |
| **(d) 단일 정률 + VAT** | **확인 안 됨 유지** | ÷1.1을 해도 **1.65%p 폭**으로 흔들린다(원 1.81%p와 거의 같다 — VAT 나누기가 편차를 거의 못 줄인다). 단일 정률 구조라면 ÷1.1이 상수에 수렴해야 하는데 아니다. 라운드 수치 수렴 근거도 없다 |

**⇒ 설계 확정 2가지**
1. **요율은 추정할 수밖에 없다** — 그러므로 계약 §4 ⓓ(`basis` 표시)는 선택이 아니라 **필수**다.
2. **요율을 단일 상수로 박으면 안 된다** — 믹스에 따라 움직이므로 **최근 완결 정산주기에서 실측해 갱신**한다(3P `option_fee_rate`의 「최신 요율을 즉시 적용」과 같은 결, 단 grain이 계정이다).

### 8-5. 보관비(`storage`) 처분 — **확정: 판매일 귀속 금지, 계정 기간비용으로 분리** (§7-3의 답)

**결정적 관측 — 매출이 0인 주기에도 storage는 계속 발생한다.**
WING2의 **6개 주기에서 RFM gmv가 정확히 0**인데 storage는 각각 **6,839 / 2,074 / 5,185 / 7,259 / 4,979 / 1,988원** 발생했다.
같은 주기에 `sale_fee`·`delivery`·`warehousing`은 **전부 정확히 0**이다.

| | WING1 | WING2 |
|---|---|---|
| storage / 매출 | 전 10주기 **0.14% 이하** (이상치 없음) | — |
| storage / 전체 정산공제 | 무시 가능 | **57.8~60.7% 상시**(매출 0인 주기는 100%) — 특정 주기 이상치가 **아니다** |
| 절대액 | — | 매출 유무와 무관하게 **1,988~7,259원에서 거의 고정** |
| 옵션 단위 storage 중 0이 아닌 행 | 126/646 = **19.5%** | 719/836 = **86.0%** |

★WING2의 비중이 큰 것은 **storage가 커서가 아니라** 매출 연동 비용(`sale_fee`·`delivery`·`warehousing`)이 0으로 떨어지는데 storage만 안 그렇기 때문이다.
**⇒ storage는 「재고를 갖고 있는 값」이 맞다는 것이 실증됐다. 판매일 축에 넣지 않는다.**
계정 기간비용으로 **분리 표시**하고, 순이익에는 창 단위로 반영한다(일할 배분은 하되 «판매»에 붙이지 않는다). 이 처분을 §4 ⓒ 보존식이 검사한다 — storage가 조용히 사라지면 보존식이 터진다.
