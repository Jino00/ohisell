- **「안전 봉투」가 실제로 문 건 86건 = 2.2%** — 병목이 아니었다. **푸는 것의 기대 이득은 작다.**
- **★`±15%`는 「가드」가 아니라 「스텝 정책」**이다(차단 기록 **0건**). `_clamp_step`이 현재가×0.85/×1.15를 그냥 돌려준다 — 더 크게 가려는 걸 자르는 게 아니라 **한 회차 이동폭의 정의**. 봉투는 **상한**(쿨다운·일일·누적·BEP·경제성)과 **속도**(±15%)로 갈리고 틀렸을 때 손해 모양이 다르다.
- **풀기를 자동화하면 안 되는 이유**: 최근 3주에 원가 177건 버퍼 · 계정 BEP 1.836→1.711 · 광고비 2배 오집계가 각각 틀렸고 **전부 「이익을 부풀리는」 방향**이었다. 틀린 성적표를 근거로 시스템이 스스로 브레이크를 푸는 구조가 된다.
- **조이기가 진짜 답답한 지점**: 손실이 확인된 상품도 하루 **−39%**(3회×15%)밖에 못 내려간다. 이건 안전이 아니라 **둔한 것**이다.
- **소급채점 stale**: 7월엔 기대(D−1)보다 하루 더 뒤처져 2,138건을 만들었다. **지금은 정상**(최신 2026-08-09 = D−1). **재발 감시 표면 없음** ← P1에서 신설.

## §3 설계 (3층)
| 층 | 내용 | 변경 주체 |
|---|---|---|
| 코드 상수 | 지금 값 그대로 — **최후 폴백** | 배포로만 |
| DB 파라미터 | `NaverAccountSettings` KV `guardrail_params`(JSON 1행) | Jino 콘솔 PUT + 승인된 제안 |
| 상황 조정 | 조이기=자동 / 풀기=제안→Jino 클릭 | 시스템(조이기만) |

### 3-1. 조이기 자동화 — 유닛별 `loss_grade` 하나로
| 등급 | 판정 (전역 규칙) | 일일 하향 상한 | 스텝 |
|---|---|---|---|
| normal | 기본 | 3회 (현행) | −15% |
| bleeding | 최신 소급채점 bleeding 보드에 있음(기존 `_bleeding_hold_reason` 신호 재사용) | **5회** (하루 −56%) | −15% |
| severe | bleeding **3일 연속 이상** | 5회 | **−30%**(기존 `_EXPLORATION_MAX_CHANGE_PCT` 값 재사용, 하루 −83%) |

- 조임의 상한선: 네이버 최소입찰가 바닥 + **쿨다운 2h는 등급 무관 유지**(진동 방어는 안 푼다).
- **★fail 방향**: 소급채점이 stale(최신 < D−1)이면 **normal로 폴백** — 낡은 데이터로 멀쩡한 광고를 −83% 내리는 것도 손해다.

### 3-2. 풀기 제안 — 근거 붙은 제안 → 클릭 한 번
- 제안 1건 = 대상 파라미터 / 현재값→제안값 / **근거 숫자와 출처**(어느 테이블·어느 기간) / **입력 신선도 스탬프**.
- 트리거는 전부 「지속 조건」형(예: *최근 14일 쿨다운에 물린 건 중 사후 채점에서 「막힌 방향이 옳았을」 비율 < 30%* → 쿨다운 2h→1h 제안). **정확한 수치는 P3 착수 시 실측으로 정한다** — 지금 못 박으면 근거 없는 단정이다.
- 승인 경로: 기존 `expert-delegation` PUT과 같은 패턴(콘솔 PUT, 사람만).
- 남용 방지: 같은 파라미터 재제안 **쿨다운 14일** · 승인·기각 이력 누적(사후 가시성).

### 3-3. 되먹임 차단 — 어디까지가 필요한가
| 장치 | 판단 |
|---|---|
| 풀기는 전부 사람 승인 | **필요** — 이것만으로 «자동» 루프가 끊긴다 |
| 제안 **생성** 전 신선도 게이트(소급채점 D−1 ∧ BEP 스냅샷 당일 ∧ 원가 드리프트 검사기 exit 0) | **필요** — 틀린 입력은 제안서 자체를 오염시키고, 그러면 사람 게이트가 형식이 된다. 신선하지 않으면 **제안을 안 만든다**(fail-closed) |
| 조이기의 stale 폴백(§3-1) | **필요** |
| 광고비 이중집계 실시간 검산을 풀기 게이트에 추가 | **과잉** — 사람 승인 + 신선도 스탬프로 충분. 검산은 별도 상설 표면(B-2)의 몫 |

### 3-4. 파라미터 위치
- `NaverAccountSettings` KV 1행(`guardrail_params`, JSON) — **마이그레이션 0**.
- fail 방향: KV 없음/파싱 실패 → **코드 상수 폴백**(fail-to-current). 상수는 지우지 않는다.
- **되돌림 스위치 한 줄**: `guardrail_gate._PARAMS_FROM_DB = True` → False면 전부 코드 상수로 원복.
- **전역 1행만.** 캠페인별 파라미터는 비목표(개별 캠페인 하드코딩 금지 규율과 정합).

## §4 단계 (각 단계가 독립 승인·배포 가능)
| Phase | 내용 | Jino에게 보이는 것 |
|---|---|---|
| **P1** | 파라미터 DB층 + 폴백 + **봉투 현황판**(read-only) + **소급채점 stale 배너** | 콘솔에서 "지금 봉투가 뭘로 돌고 있나"가 처음으로 보임 |
| **P2** | 조이기 자동화(`loss_grade`) | 현황판에 유닛별 등급 표시 |
| **P3** | 풀기 제안 + 승인 버튼 | 제안 카드 + 클릭 한 번 |

**P1만으로도 가치가 있다**(가시성 + 원복 스위치). P1 착수를 권한다.

## §5 합격기준 — 라이브 증거
**재개 없이 관측 가능 (P1)**
1. KV에 테스트 값 투입 → 현황판이 `cooldown=1h · 출처=DB` 표시 → KV 삭제 → `출처=코드상수`로 복귀 (폴백 라이브 증명)
2. 현황판에 현재 유효값·출처가 전부 표시
3. **소급채점 stale 배너**: 최신 채점일 < D−1이면 콘솔 경고(2,138건 병목의 재발 감시 — 지금 없음)
4. (P3) 풀기 제안 생성기를 과거 데이터로 드라이런 → 제안 JSON에 근거·신선도 스탬프 포함 관측

**재개해야만 관측 가능 — 부채로 명시하고 넘어간다**
5. bleeding 유닛에 일일 4회 이상 하향이 실제 집행됨
6. 제안 승인 클릭 → 다음 레인부터 새 값으로 집행

> PUT 200·테스트 통과는 합격이 아니다. 적대 리뷰 1회 + 변이 주입 필수.

## §6 이번에 안 하는 것 (비목표)
- **풀기의 자동화** — 재개 후 1개월 실적이 쌓인 뒤 재논의(Jino 합의)
- **±15% 스텝의 상향**(풀기 방향 속도) — 스텝은 조이기 방향(−30%)만 건드린다
- 예산 변경 개방 (스프린트 금지선)
- **소급채점 파이프 자체 수리** — 감시 배너만 이번 범위
- ML/학습 기반 파라미터 · 캠페인별 개별 값
- `auto_operate`·`optimizer` 재개

## §7 금지선
- 봉투를 **푸는** 방향의 자동 변경 금지(사람 승인 필수)

- 코드 상수 삭제 금지(최후 폴백)
- 개별 캠페인 하드코딩 금지
- 신선하지 않은 입력으로 제안 생성 금지(fail-closed)
