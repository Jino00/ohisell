# ref 89 — RG 매출 원장 괴리의 원인 (읽기 전용 조사)

> 2026-08-21 KST · 세션 `586fba5c` · 트랙 「쿠팡 손익 정합 (2계정 4채널)」 / `track_coupang-rocket-1p.md`
> 발단: Jino가 Wing 콘솔 판매분석(오하이테크·로켓그로스·최근 30일)을 캡처해 보임 — 콘솔 3주문 45,000원.
> 우리 원장은 같은 창에서 5건 68,900원. **조사만 했다. 코드·prod·DB 변경 0건.**

## 0. 한 줄 결론

**우리 RG 매출 원장은 쿠팡 «주문 API»와 원 단위로 일치한다(수집 결함 아님). 괴리는 쿠팡의 두 표면 사이에 있다 —
주문 API는 gross(취소·반품 포함)이고 콘솔 판매분석은 net이다. 그리고 RG 주문 API에는 취소·상태 축이 아예 없어서
주문 원장만으로는 net을 만들 수 없다.**

## 1. 선행 이력 (이번이 처음이 아니다)

| 시점 | 판정 | 갭 | 좌표 |
|---|---|---|---|
| 2026-06-14 | **「결함 아님 — gross vs net 기준 차이」로 종결(D-11)** | ~5.1% | `docs/tracks/completed/track_coupang-revenue-ad-reconciliation.md:31` |
| 2026-08-12 | 재측정, 기준선 초과 — 미해결 이월 | +8.10% | `docs/references/55_ofix_rg_diagnosis_20260812.md:186,356` |
| 2026-08-20 | 재측정, 「원인 미상·조사 대상」으로 이월 | 12% | `HANDOFF_dashboard-rg-revenue-wiring_20260820.md` §3-3 |
| 2026-08-21 (이번) | 원인 확정 + 대안 원장 확인 | **+11.8%** | 이 문서 |

D-11의 «gross vs net» 가설은 **맞았다.** 다만 그때 「메울 소스가 시스템에 없다」고 본 것은 **틀렸다** — 소스는
있었고(§4) 우리가 이미 매일 수집하고 있었다.

## 2. 확정된 사실 (전부 라이브 관측, 2026-08-21)

**① 우리 원장 == 쿠팡 RG 주문 API.** WING2 07-23~08-21 창을 API에 재조회 → **5건 68,900원**, 우리 DB와 건·금액 동일.
→ 수집 누락도 중복도 아니다.

**② RG 주문 API에 취소·상태 필드가 없다.** 목록(`/rg/orders`)·단건(`/rg/order/{id}`) 둘 다.
콘솔이 되돌린 건(08-14 14,100원)과 정상 건(08-20 14,100원)의 응답이 **필드 집합까지 동일**하다 —
`vendorId·orderId·paidAt·orderItems[vendorItemId·productName·salesQuantity·unitSalesPrice·currency]`.
→ 우리가 상태를 «버린» 것이 아니라 쿠팡이 «안 준다». (수집기 `rg_order_sync.py`에 cancel/status/refund 매칭 0건)
⚠️ **증거 등급 구분**: 「수집기·클라이언트에 상태 축이 없다」는 코드로 누구나 재현 가능하다. 그러나 「두 건의 실제 API 응답 필드셋이 동일했다」는 **라이브 API 호출로만 재현된다** — 완료 QA(읽기 전용·API 호출 금지)는 이 부분을 재현하지 못해 판정불능으로 분류했다.

**③ 원장은 append-only.** `coupang_rg_order_item` 전건 `synced_at == created_at`.
→ 한 번 쓴 행이 사후에 갱신·삭제되는 경로가 구조적으로 없다.

**④ 콘솔 숫자를 우리가 이미 수집하고 있다.** `coupang_vendor_summary_daily`의 `registration_type='RFM'`이 로켓그로스다.
WING2 07-23~08-21 RFM 합계 = **45,000원 / 3개** — Jino가 캡처한 콘솔 화면과 **정확히 일치**.

**⑤ 오픽스(WING1) 30일(07-22~08-20) 재현:**

| | 매출 | 수량 |
|---|---|---|
| 우리 원장 | 5,900,470원 | 345 |
| 콘솔(RFM) | 5,206,400원 | 311 |
| 차이 | **+694,070원 (+11.8%)** | **+34개** |

**⑥ 차이는 일방향이다.** 30일 중 «우리 < 콘솔»인 날이 **0일**. 우리가 항상 크거나 같다.
→ 타임존·귀속일 이동이 원인이면 양방향이 나와야 한다. 아니다.

**⑦ 갭은 «단가»가 아니라 «건수»다.** 30일 중 **9일이 원 단위로 완전 일치**(차이 0) — 07-26·07-29·07-31·08-03·08-04·08-05·08-06·08-16·08-19.
(초판에 「8일」로 적었던 것을 완료 QA가 라이브 재계산으로 정정했다 — 결론 방향은 불변이고 오히려 더 강해진다.) 단가가 계통적으로 어긋나면
그런 날이 안 나온다. 수량 차이(345 vs 311)가 직접 뒷받침한다.
→ **D-CPP-6(「`unit_sales_price`는 등록가라 할인이 안 보인다」)는 이 갭의 원인이 아니다** — 적어도 이 창에서는.
(그 자체의 유효성은 별개 — 여기서는 «이 갭을 설명하지 못한다»만 말한다.)

**⑧ 3P는 완벽히 맞는다.** 같은 날들에서 우리 3P(`orders`) == 콘솔 NORMAL 원 단위 일치
(08-08 59,400 / 08-09 19,800 / 08-17 19,800). **문제는 RG 전용이다.**

**⑨ 반품 원장은 RG를 하나도 안 담는다.** `coupang_return_item` 58행 ∩ RG 주문 2,693개 = **0건**.
(코드도 같은 말을 한다 — `intelligence.py:210` *"반품(CoupangReturnItem)은 3P 전용이다."*)
→ 「반품 원장에 없다」는 「반품이 없었다」의 증거가 아니다.

**⑩ 콘솔은 두 방식으로 net을 만든다.**
- 반품(출고 후) → **반품일에 음수**. 실례: WING2 08-14 +14,100 → **08-16 −14,100 (−1개)**.
- 취소(출고 전) → **원 판매일에서 소급 제거**. 음수 발생일이 전 계정·전 기간 통틀어 3일뿐인데
  누락은 34개라, 대부분이 이 경로다.

**⑪ 대안 원장의 가용성.** `coupang_vendor_summary_daily` — WING1 2026-06-07~08-20(75일), WING2 06-12~08-20(70일),
**결손 0일**, 매일 갱신(`last_refresh` 2026-08-21).

## 3. 확정 못 한 것 (추정으로 채우지 않는다)

- **오픽스 34개 누락 건의 «신원»** — 건별로 어느 주문인지 못 짚는다. 취소 원장이 RG를 안 담고(⑨) API가 상태를 안 주기(②) 때문이다.
  08-13 하루(갭 136,630원·6개)는 조합이 **{37,630×1, 19,800×5}로 유일하게** 떨어지는 것까지 확인했으나, 그 6건이 어느 주문인지는 미상.
- **WING2 08-09 9,800원 1건이 콘솔에 아예 없는 이유** — 취소가 유력하나 확인 경로 없음.
- 위 둘은 **판정불능**이다. 「취소일 것」이라고 적지 않는다.

## 4. 설계 함의 — 배선을 어떻게 바꾸는가

**주문 원장에 「취소 축을 같이 붙인다」는 선택지는 존재하지 않는다.** 붙일 원료가 API에 없다(②).
net RG 매출의 **유일한 소스는 `coupang_vendor_summary_daily`(RFM)**다.

그런데 그 원장은 **일별 GMV·수량만** 있고 **옵션(상품)별 분해가 없다.** 그래서 배선이 셋으로 갈린다:

| 안 | 회사·채널 소계 | 상품별 손익 | 대가 |
|---|---|---|---|
| **A. 콘솔 요약(RFM)을 매출로** | 정확(net) | **불가** | 상품별 분해·광고 귀속을 잃는다 |
| **B. 주문 원장 유지**(현 계약 전제) | **+11.8% 과대** | 가능 | 손익이 실제보다 좋게 보인다 |
| **C. 소계는 요약, 상품 분해는 주문 원장 비율로 배분** | 정확 | 근사 | 배분이 추정이다 — 금지선(추정 배분) 저촉 여부 판단 필요 |

★**이 조사는 승인 대기 중이던 계약의 전제를 무너뜨린다.** 그 계약은 「우리 원장(전자)으로 맞춘다」였고
합격기준 ⓒ가 「대시보드 RG 매출 == 종합 조망」이었다. 그대로 가면 **11.8% 과대를 화면에 고정**하게 된다.
⇒ 계약 목표 변경 = 새 계약(전역 §1 승인 지점 ①). **Jino 결정 필요.**

## 6-1. 무엇이 있었나

**`coupang_vendor_item_sales_daily`** — 그레인 `(sale_date, account_key, vendor_item_id, registration_type)`,
값 `gmv · units_sold · total_orders`. **즉 «일자 × 옵션» net 원장이다.** RFM = 로켓그로스.
원천은 콘솔 판매분석 화면의 백킹 API(`POST /tenants/rfm-ss/api/business-insight/vi-detail-search`) —
**Jino가 캡처한 그 화면의 「옵션 ID」 필터가 바로 이 표면이다.** D-CPP-36(2026-08-10)이 이미 개통해 매일 돌고 있었다.

**§2④에서 「일별 GMV·수량만 있고 옵션 분해가 없다」고 쓴 것은 `coupang_vendor_summary_daily`(요약축)에 대해서만 참이다.**
옵션축 원장이 그 옆에 따로 있는 것을 못 봤다.

## 6-3. 그래서 무엇이 달라지나

- **A안의 유일한 대가가 사라진다.** 「콘솔 net을 쓰면 상품별 분해를 잃는다」는 **거짓**이었다 — 옵션 grain이 이미 있다.
- **원가 문제도 같이 풀린다.** §4가 고심한 「매출은 net인데 원가는 gross」는, 옵션별 net 수량 × 옵션 원가로 **실측 계산이 된다.** 추정 배분이 필요 없다.
- **갭의 국소화도 된다.** gross 주문 원장과 옵션축 net을 «옵션 × 일» 셀로 조인하면 차이가 셀 단위로 떨어진다.
  Fable 실측: WING1 08-05~08-20 불일치 셀 12개. §3이 「신원 미상」이라 한 08-13 갭 6개 중 5개가 두 셀에 떨어진다.
  ⚠️ 다만 일부는 콘솔 귀속일과 `paid_at`의 날짜 경계 이동으로 ± 셀이 쌍을 이룬다(양방향 조인 필요) — **완전 해소는 미검증**.

## 6-4. 남은 제약 (이것도 실측)

- **커버리지가 짧다**: 옵션축은 WING1 **2026-08-05~**(16일)·WING2 **07-27~**(23~24일)뿐이다. 요약축(WING1 06-07~)보다 훨씬 짧다.
  원인은 페처 config `vi_days` 기본 **7일 롤링**(`tools/wing_browser_fetcher.py:238`).
- **백필 경로는 있다**: `vi_days`를 일회 확대. ★단 서버 `CONSERVATION_WINDOW_DAYS`(`scheduler_health.py:498`, 현재 7)를

## 6-5. 아직 안 연 것 (다음 후보)
