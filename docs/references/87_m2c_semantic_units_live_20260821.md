## 0. 이 슬라이스가 푼 문제

쇼핑 검색어 제외가 후보를 **한 건도** 못 만들었다. 원인은 하류가 막힌 게 아니라 **상류가 0**이다 — 한국어 쇼핑 검색어의 97.4%가 「갤럭시폴드8내부필름」처럼 토큰 1개라 개별 grain에서 `clk>=10` 통과가 107,099행 중 11건뿐이고 그 11건도 화이트리스트에 걸린다. 그래서 **ⓒ가 ⓔ보다 먼저**다(D-NAO-190: *"ⓔ는 후보를 만들지 못한다 — 실제 해제 레버는 ⓒ"*).

## 2. 적대 리뷰 1R FAIL(P1 2) → 2R PASS

### P1-1 — 화이트리스트가 의미 단위 경로에서 무력화
화이트리스트 토큰이 **의미 사전 원소이기도 한데**(프로토타입과 동일, 분절용) 집계 후 게이트가 없었다. 리뷰어 재현: 「아이폰{i}케이스」 11건이 개별 grain에선 화이트리스트로 **전부 보호**(후보 0건)인데 의미 단위에선 「아이폰」 하나로 풀링돼 `clk=55·cost=11,000`으로 통과, `pending` 제안이 생성됐다.
⇒ 기존 `_build_whitelist`/`_is_whitelisted` **동일 함수**를 unit/pair phrase에 적용(새 정책·상수 0).
⇒ **잔여에는 적용하지 않았다** — 최장일치 스캔의 정의상 잔여 구간은 사전 단어를 부분문자열로도 포함할 수 없어 항상 no-op. 2R이 `segment_indexed`(:92-113)를 읽고 불변식 검증, 반례 없음. ⚠️단 이 불변식은 `_build_whitelist`와 `build_vocab`의 토큰화 규칙이 **두 파일에 중복 정의**된 채 동기화돼 있어야 성립한다(§4 이월).

### P1-2 — dedup 키가 target_type을 안 봐서 실행 가능한 제안이 막힘
리뷰어 재현: 의미 단위 pending(「블루투스」, 영구 비실행)이 있으면 나중에 실제 검색어 "블루투스"가 개별 grain 게이트를 통과해도 `shopping_deduped=1`로 억제돼 **실행 가능한 제안이 끝내 안 생겼다.** D-NAO-180·181로 어렵게 연 경로가 막히는 것.
⇒ `_has_open_or_executed`에 `target_type` **필수 인자**(기본값 없음 — 빠뜨리면 `TypeError`, 조용한 오작동 불가) + 호출부 4곳 갱신 + 교차 테스트 2건.

### 변이
1R 주입 7종 중 **2종 생존**(pair per-term dedup · semantic cap 경계) → 테스트 추가 → 2R 재주입에서 **둘 다 사망**.

## 3. ★라이브가 잡은 세 번째 결함 — 2R PASS 뒤에 나왔다

배포 후 실측: `naver_campaign_settings` **9행 전부 `optimizer='none'` / `auto_operate=0`** — `auto_operate=1`이 **0건**(PAO 전면 정지 D-NAO-132).

구현이 `_in_scope`(=`auto_operate`) 게이트를 **의미 단위 후보 생성 앞**에 뒀으므로 ⇒ **모든 후보가 `out_of_scope`로 떨어져 pending 제안이 영원히 0건.** 방금 만든 판정층이 **아무것도 산출 못 하는 부품**이 될 뻔했다.

**계약 §4-4 원문과 어긋난다**:
> *"항상 판정층까지만 만들고 실행은 기존 잠김에 맡긴다 — … 잠김 2(승인원)·잠김 3(optimizer, `naver_execution_harness.py:2490` OptimizerGuardError)이 살아 있는 것 자체가 S1 합격기준 ⑤의 라이브 증거이기 때문이다."*

잠김 3은 **실행 경로**에 있어야 하고 그것이 실행을 막는 모습이 곧 증거다. 후보 «생성»을 막으면 증거가 될 대상 자체가 사라진다.

**수정(범위 축소)**: 의미 단위 경로에서만 `_in_scope` → `_has_valid_adgroup`(sentinel·빈 adgroup 위생만). 근거 = 의미 단위 제안은 `target_type='search_term_semantic'`이라 **harness 구조 가드가 실행을 영구 차단**하므로 `auto_operate` 게이트는 **중복**이다. **개별 grain 경로(`target_type='search_term'`, 실행 가능)의 `_in_scope`는 유지.**

★**리뷰어가 이걸 못 잡은 이유**: 워크트리에 prod 데이터가 없어 「가능성은 실재하나 `shopping_out_of_scope`로 관측 가능해 설계대로」로 판정했다. **격리 성공은 필요조건이지 충분조건이 아니다** — 이번 슬라이스에서 두 번째로 확인됐다(C10 `get_naver_config` 사고와 같은 형태).
