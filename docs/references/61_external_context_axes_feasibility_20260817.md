## C. 외부 신호 — 시계열인가 현재값인가

**`/keywordstool` — 현재값(스냅샷)만, 소급 시계열 불가.** 스펙 파일(`spec_ncc-keywordstool.json`) 정의 인용:

- `monthlyPcQcCnt`: *"Sum of PC query counts **in recent 30 days**."*
- `monthlyMobileQcCnt`: *"Sum of Mobile query counts **in recent 30 days**."*
- `monthlyAvePcClkCnt`/`monthlyAveMobileClkCnt`/`monthlyAvePcCtr`/`monthlyAveMobileCtr`/`plAvgDepth`: *"...**in recent 4 weeks**."*
- `compIdx`: *"A competitiveness index **based on PC ad**."* — 시점 파라미터 없음.

응답 스키마(`RelKwdStat`) 전체에 과거 특정 월을 지정해 값을 받는 필드가 없다. 요청 파라미터에 `month`(정수, "예: 12")와 `event`(계절 테마 ID)가 있지만 설명은 *"Seasonal theme"*이고, 응답 스키마는 여전히 "최근 30일/4주" 값 하나뿐이다 — 이 두 파라미터는 **키워드 추천의 테마 필터**(예: "12월 관련 키워드 추천")로 읽히지, 「그 달의 과거 검색량」을 반환하는 시계열 파라미터가 아니다. 이 문서만으로 `month`/`event`의 소급 조회 가능 여부를 단정할 수 없으나(호출해 보지 않았다 — 지시에 따라 API 미호출), **응답 스키마에 월별 값이 없다는 사실은 확정**이다.

**결론: 계절성을 이 API의 검색량으로 소급 측정하는 것은 원리적으로 불가**(호출 시점의 최근 30일 스냅샷만 얻을 수 있고, 1년 전 특정 시점의 검색량은 이 API로 재구성 불가). ref 59 §③-4(A9)가 이미 이 축을 「당김(비용 상위 컷)」으로 두면서 용도를 "**확장 방향 선별**"(현재 시점 기준 볼륨 대비 점유 판단)로 한정한 것과 정합한다 — **계절성 축으로 오용하면 안 된다**는 점을 이번 조사가 스펙 근거로 확정했다.

`compIdx`(경쟁도)도 동일 — *"based on PC ad"*, 시점 지정 불가. **판정: 둘 다 현재값**.

1. **§③-1(층화 변수)에 «요일·공휴일·설/추석 연휴» 축을 추가한다** — 지금 ref 59엔 계정 자체의 요일/공휴일 축이 명시적으로 없다(⑦-1이 "요일 계절성은 28일 롤링창이 자동 상쇄한다"고만 함 — 이건 **상쇄 처리**지 **관측 축**이 아니다). Jino의 원 지시("휴일·주말")가 요구하는 것은 **밴드가 공휴일·연휴에 체계적으로 달라지는가**를 직접 보는 것이므로, §③-3에 S급 또는 A급 축으로 `is_kr_holiday`·`is_seollal_chuseok_window`·`weekday`를 추가해야 한다. 비용 0(계산), API 콜 불필요 — 승인분 콜 수(2,200)에 영향 없다.
2. **§③-2/§4-1에 「제품 축」의 데이터 원천을 명시한다**: `naver_entity.name`(정규식 파싱, 모델 정규화 전처리 필요)과 `naver_entity.reg_tm`(램프업 프록시, 이미 「당김」 표시된 A2/A4 인근에 넣을 것) — 단 **`product_master.created_at`을 출시일로 쓰려는 시도는 이 조사로 원천 차단**한다(일괄 이관 시각).
3. **§③-4(외부 신호)의 A9 서술을 강화한다**: "계절성 측정 불가"를 가정이 아니라 **스펙 인용 근거로 명문화**(§C). 현재 ref 59는 "당김(비용 상위 컷)"이라고만 하고 이 함정을 명시하지 않았다.
4. **§④(데이터 출처)에 D축(스마트스토어 주문)을 신규 재료로 추가할지는 Jino 결정** — 추가한다면 「2026-03~ 5.5개월 창」이라는 커버리지 라벨을 §⑤-8(커버리지 착시 함정)과 동일한 규율로 강제해야 한다.
5. **⑦-2(통제 불가/경보 표)의 "검색 수요 변화" 행을 그대로 유지**하되, 이번 조사로 그 옆의 "프록시=우리 노출수·활성 검색어 수" 서술이 **유일한 선택지임이 더 확정**됐다(외부 검색량 시계열이 원리적으로 없으므로).
6. **「휴가 시즌」·「단말 출시일(비-아이폰)」은 §④-3(원리적으로 못 얻는 것) 표에 새 행이 아니라 별도 취급이 필요** — 원리적 불가가 아니라 **①정의 필요 ②외부 사실 확인 필요**라는 다른 성격의 갭이다. ④-3에 섞으면 "불가"로 오독된다.

## ★Jino 결정이 필요한 것

1. **「휴가 시즌」의 조작적 정의 — 후보 3안** (라이브러리로 못 준다, 공휴일이 아니므로):
   - **(a) 고정 날짜 관습형**: 예컨대 "7월 마지막 주~8월 둘째 주"처럼 매년 같은 달력 구간을 하드코딩. 장점: 재현 가능·해석 쉬움. 단점: 숫자를 지어내야 한다(왜 그 2주인지 근거가 필요) — 이번 조사에서 그 정확한 관습 구간을 확인할 자료가 없다(외부 확인 필요, §비고).
   - **(b) 우리 매출 데이터 역산형**: 채널6 주문량의 요일 조정 후 잔차가 특정 구간에서 계절 평균 대비 유의하게 낮은/높은 구간을 "휴가 시즌"으로 정의. 장점: 우리 계정의 실제 반응을 반영. 단점: §D에서 확인했듯 채널6 주문 데이터가 5.5개월뿐이라 **2025년 여름은 이 방법으로 절대 못 잡는다** — 2026년 여름(7~8월) 하나만 관측되므로 "패턴"이라 부르기엔 n=1.
   - **(c) 이번 분석에서 제외**: 정의가 없으면 축을 만들지 않고, ref 59 §④-3(원리적 불가)이 아니라 "정의 미확정으로 이번 라운드 보류"로 명시적으로 적는다.
   - 조사자 의견 없음(설계 판단은 Jino 몫) — 다만 (b)를 쓰더라도 2025년 여름 재현은 안 되므로, (a)·(c) 중 택하거나 (a)의 정확한 날짜 구간을 **Jino가 실제 업계 관습대로** 확정해야 한다(임의 추정 금지).

2. **비-아이폰 단말(갤럭시 S/Z/A, 갤럭시탭, 아이패드) 출시일 — 외부 확인 필요, 조사자가 기억으로 채우지 않았다.** §B에서 확인된 실제 캠페인·그룹 대상 모델은 다음과 같고, 이 목록의 정확한 한국 정식 출시일을 Jino가 확인(또는 확인 지시)해야 `iphone_launch_dates.json`과 같은 형식의 설정 파일을 만들 수 있다:
