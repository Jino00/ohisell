## 3. 응답 원문 — §7-2 `[미상]`이 일부 풀렸다

```json
{"success":true,"returnMessage":"success","code":"0","result":"SUCCESS"}
```

★ref 106 §3은 실패 시 `alert(data)`뿐이라 **「구조화된 에러 메시지가 없다」**고 적었고, 그래서 계약 §7-2가
「부분 실패의 표면」을 `[미상]`으로 남겼다. **성공 응답은 구조화돼 있다** — `success`(불리언) 외에
`returnMessage`·`code`·`result` 세 필드가 더 온다.

- ⇒ 우리 판정기(`_success_flag`)는 `success` 불리언만 읽는데, 그것으로 **충분했다**(성공 케이스 실증).
- ⇒ **`[미상]`이 완전히 풀린 것은 아니다**: 이건 «성공 응답»의 모양이고, **실패 응답의 모양은 여전히 미상**이다.
  `code`가 `"0"`이 아닌 값을 주는지, `returnMessage`에 사유가 실리는지는 실패가 한 번 나야 안다.
- ⇒ 그래서 `response_body` **원문 보존**(계약 §3 금지선)이 옳았다. 실패가 처음 났을 때 유일한 재료다.

## 6. ★부수 관측 — 재수집이 굳은 건을 되살렸다 (결함 아님)

실행 후 재수집 직후 RI 큐가 **살아있음 6건(2,401,425원) / 굳음 8건**으로 갈렸다(실행 전 15/0).

| | 실행 전 | 실행 후 |
|---|---|---|
| 살아있음 | 15건 7,299,040원 | **6건 2,401,425원** |
| 굳음 | 0건 | **8건** |
| 계 | 15 | 14 (카나리 1건이 CI로 빠짐) |

이 8건은 수집 창(발주일 기준) 밖이라 `synced_date`가 2026-08-27에 멈췄고, 마지막 수집일이 08-28로
넘어가면서 굳음으로 재분류됐다. **전부 `can_request=false` · 사유 「재수집 후 확인 가능」**로 막혀 있다.

★이게 왜 중요한가: 완료 QA(08:5x)가 「현재 굳음 0건이라 **굳은 행 분기를 라이브에서 볼 수 없다**」고
판정불능으로 남긴 항목이 **여기서 실물로 관측됐다.** 굳음이 생기는 것은 병이 아니라 수집 창의 구조이고,
화면은 그 상태에서 **누르는 경로를 원천 차단**한다 — 계약 §2가 요구한 대로다.

## 7. 이 카나리가 답한 것 / 못 답한 것

**답한 것**
- 요청 규격이 실제로 통한다(경로·바디 없음·CSRF 없음 — ref 106 §3 실측이 옳았다)
- 사전 GET 게이트가 라이브에서 `button_present`를 정확히 판정한다
- 성공 응답의 모양(§3)
- 전이 즉시성(§7-4 `[미상]`): 응답 직후 supplier 상태는 바뀌어 있고, **우리 원장 반영은 재수집에 달렸다**(37초 뒤)
- 세션 만료 중에도 자가 복구가 끼어들어 실행이 성립한다

**못 답한 것 (여전히 `[미상]`)**
- **멱등성** — 이미 CI인 건에 POST하면? **여전히 호출한 적 없다.** 사전 GET 게이트가 그 상황을 안 만든다(설계대로)
- **실패 응답의 모양** — 성공만 봤다. `code`≠`"0"`이 어떻게 오는지 미상
- **되돌리기** — 시도하지 않았고, 경로가 화면에 없다는 판정은 그대로다
- `already_confirmed`(버튼 없음)·`unknown`(결과 미상) **두 종결 상태의 라이브 발현** — 아직 0건
