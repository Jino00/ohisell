## §0. 한 문단 요약

ADVoost는 네이버 GFA 산하의 **완전자동 쇼핑 캠페인**이고, 광고주가 정하는 것은 「쇼핑몰 연결」과 「예산」 둘뿐이다. **PAO가 이것을 자동 운영하는 것은 불가능하다** — 이유가 둘이고 둘 다 독립적으로 치명적이다: ①**권한 게이트** — GFA API는 베타·공식 파트너사 한정이고 우리는 자격증명 자체가 0건이다(비용이 자동 수집되는 것은 GFA 접근이 아니라 **검색광고 API의 비즈머니 청구서**를 읽는 것이다) ②**표면 부재** — 게이트를 넘어도 PAO의 쓰기 함수 9개 중 3~4개만 개념적으로 대응하고, 무엇보다 ADVoost는 **사람조차 입찰을 못 건드리는** 상품이라 「총이익 기준 입찰 최적화」라는 PAO의 존재 이유가 꽂힐 구멍이 없다. 다만 **ADVoost의 AI가 우리 원가를 모른다**는 정황은 실재하며, 그 비대칭을 쓸 수 있는 자리가 하나 남는다 — **어떤 상품을 광고 대상에 넣을지**(콘솔 에셋그룹 필터). 이건 자동화가 아니라 **보고서**다.

## §1. 「우리는 이미 접근 권한이 있는가」 — 아니다 (가설 반증)

세션이 세운 가설: *"`sync_naver_display_ad_costs` 크론이 GFA 비용을 자동 수집하니, 우리는 이미 GFA API에 인증돼 있을 수 있다. 그렇다면 「베타·파트너 한정」이라는 기존 결론이 틀린 것이다."*

**반증됐다.** 코드 좌표:

| 항목 | 실측값 | 좌표 |
|---|---|---|
| 실제 호출 엔드포인트 | `GET /billing/bizmoney/histories/exhaust` | `naver_sa_ad_fetcher.py:254` (`fetch_bizmoney_exhaust_daily`) |
| base URL | `https://api.searchad.naver.com` — **검색광고(SA) 도메인** | `naver_sa_ad_fetcher.py:24` |
| 인증 | `NAVER_SA_ACCESS_LICENSE` / `NAVER_SA_SECRET_KEY` / `NAVER_SA_CUSTOMER_ID` (HMAC 서명) | `naver_sa_ad_fetcher.py:25-27` |
| 호출부 | `sync_display_ad_costs` | `naver_display_ad_costs.py:74` |
| GFA 전용 자격증명 | **0건** — `grep -rn "GFA_CLIENT\|NAVER_GFA\|gfa.naver.com\|ADVOOST_"` 전건 0. prod `.env`에도 없음 | 코드베이스 전수 |
| `NAVER_CLIENT_ID`/`SECRET` | 존재하나 **네이버쇼핑 상품메타 검색 API용** — GFA와 무관 | `backend/tests/test_naver_product_meta.py:312-313` |

**기제**: 비즈머니(충전금)를 NCC(검색광고)·PMAX(ADVoost)·GFA(디스플레이) **세 상품이 공유**한다. 그래서 SA API의 청구 내역에 상품코드별 차감액이 **얹혀** 나온다.

> ★**「청구서 열람권」을 「계정 접근권」으로 읽을 뻔했다.** 비용 숫자가 자동으로 들어온다는 사실이 접근 권한의 증거처럼 보이는 구조였다. 인증 체계가 다르다(SA HMAC vs GFA OAuth Bearer)는 것이 결정적 반증이다.

**⇒ 기존 결론(북극성 §4-5·트랙:475 「성과형 디스플레이 API가 베타 + 공식 파트너사 한정」)은 틀리지 않았다.**

신청 경로: `https://naver-ad-api.github.io/openapi-guide/docs/prepare/developers-my-application`

> "등록된 내 애플리케이션에서 Client ID 값을 복사하고, 네이버 성과형 디스플레이 광고 사이트에 접속하여 대표 관리 계정 > 설정 > API 관리 메뉴의 'API 사용 신청'을 통해 Client ID 를 등록해 주시면, 관리자 확인 후 API 사용 권한이 부여될 수 있습니다. **(단, 테스트 기간 동안은 일부 관리 계정에서만 API 사용 신청이 가능합니다.)**"

**3단계 게이트**: ①네이버 개발자센터 OAuth 앱 등록 → ②GFA 콘솔 「API 관리」에 Client ID 등록 → ③네이버 관리자 승인. 베타 기간엔 **일부 계정만 신청 자체가 가능**하다.

★**게이트는 조회·쓰기를 구분하지 않는다** — API 전체에 같은 문이 걸린다. 「성과 조회는 열려 있고 쓰기만 막혀 있다」는 구분은 성립하지 않는다(우리는 조회도 못 한다).

## §4. PAO 조작 어휘 ↔ GFA 대조 — 게이트를 넘어도 안 맞는다

PAO 쓰기 함수는 `backend/app/services/naver_ad/naver_sa_writer.py`에서 전수 추출(전부 `/ncc/*` = SA API).

| PAO 함수 (좌표) | 실제 조작 | GFA 대응 |
|---|---|---|
| `set_campaign_lock`(:959) | 캠페인 정지/재개 | ✅ `POST /campaigns/activate` |
| `set_adgroup_lock`(:937) | 광고그룹 정지/재개 | ✅ `POST /adSets/activate` |
| `update_adgroup_bid`(:1149) | 광고그룹(쇼핑) 입찰가 | ✅ `POST /adSets/edit` (BidPrice) |
| `update_campaign_budget`(:988) | 캠페인 일예산 | △ `editSpendLimit`은 「지출한도」 — **DAILY/TOTAL은 GFA에선 adSet 계층**(계층 불일치) |
| `update_keyword_bid`(:820) | **키워드** 입찰가 | ❌ **개념 없음** |
| `set_keyword_lock`(:916) | 키워드 정지/재개 | ❌ **개념 없음** |

| `add_exclusions`·`add_restricted_keywords`·`delete_restricted_keywords`(:542,:606,:722) | 제외키워드 | ❌ **개념 없음** |
| `update_ad_bid`(:1262) | 소재 개별 입찰 | ❌ GFA는 adSet 단위 입찰만 |

★**「대응 없음」의 이유는 권한이 아니라 «개념 자체가 없어서»다** — GFA/ADVoost는 검색어 기반 광고가 아니라 **오디언스 타겟 디스플레이·쇼핑 추천**이다. PAO가 하는 일의 태반(키워드류 전부)은 그쪽에 대응물이 없다.

**대응률: 9개 중 3~4개.**

## §6. Jino 직감의 판정 — 「우리가 더 잘할 수 있나」

### 6-a. ADVoost의 목적함수 — 원가를 모른다 (정황 증거)

| 검사 | 결과 | 출처 |
|---|---|---|
| 원가/마진 입력 항목이 있는가 | **6개 소스 전부에서 0건**(공식 가이드 1 + 보도 4 + 대행사 블로그 3) | — |
| 광고주 설정 항목 | **「쇼핑몰 연결 + 하루 예산」 둘뿐** | ampm.co.kr/insight/59252 |
| 내세우는 성과 지표 | **ROAS · CVR** ("ROAS와 CVR이 도입 이전 대비 유의미하게 향상") | 동 출처 · CBT 40개사 보도 |
| 공식 문서의 목적함수 수식 | **확인 안 됨** | — |

⚠️ 이건 「공식 문서가 원가 없음을 **명시**」한 것이 아니라 「설정 항목 목록에 원가가 **없다**」는 정황 증거다. 완전한 부재 증명이 아니다.

**⇒ 우리 목적함수(총이익 절대액, D-NAO-59)와 다를 개연성은 실재한다.** 원가를 아는 것은 우리뿐이다.

### 6-b. 반대 방향 — ADVoost가 쓰는데 우리는 못 보는 신호

네이버 쇼핑·검색 지면 전체의 **지면별 반응 데이터**(광고 서버 내부 로그)를 쓰는 것은 우리가 원리적으로 접근 불가하다. 다만 **공식 문서에서 명문으로 확인하지 못했다** — [미상].
★공정성 기록: 이 조사는 **「ADVoost 실패 사례」를 별도로 검색하지 않았다.**

### 6-c. 판정

> **「이길 여지는 있으나 실행 손잡이가 없다」**

목적함수 차이는 개연성이 높다. 그러나 ①API 문이 잠겨 있고 ②넘어도 대응이 3~4/9이며 ③**입찰은 아무도 못 만진다.** 이 사슬에서 「더 잘한다」는 주장이 닿을 자리가 없다.

### 6-d. ★단 하나 남는 자리 — 어떤 상품을 광고에 넣을지

2차 출처(`inside.ampm.co.kr/insight/13708`, **1차 아님**):

> "상품별로 광고를 나누어 운영하는 경우 **에셋 그룹 설정 → 아이템 세트 → 모든 아이템 → 필터 조건**을 통해 광고할 상품 조건 지정"

ADVoost의 AI가 원가를 모른다면, **마진 낮은 상품을 애초에 광고 대상에서 빼는 것**이 우리가 총이익 방향으로 개입할 수 있는 유일한 지점이다. 그리고 그 판단(어느 상품이 마진이 낮은가)은 **광고 축 없이 원가·매출만으로 답할 수 있어서 지금 데이터로도 가능하다** — 상품 축 광고 성과 원장(별건, 계약 §1 「안 하는 것」)이 없어도 된다.

⇒ 정확한 표현: **「PAO가 자동 운영」은 불가**이고, **「PAO가 상품별 마진 재료를 대고 사람이 콘솔에서 반영」은 가능**하다. 후자는 자동화가 아니라 **보고서**다.
⚠️ **[미상]**: 상품 단위 include/exclude가 API로도 되는지(§3 마지막 행) — 되면 훗날 자동화 여지가 생기고, 안 되면 영구히 사람 클릭이다.

⇒ ref 65 §2의 *"6엔 기법이 아니라 관측 요구의 기록을 배치한다"*는 결론은 **6%가 아니라 8.5~13% 위에서 다시 판단할 재료**가 된다.

### ★ⓓ가 닫히면서 확정되는 것 (2026-08-25 08:0x)

Jino 원문: *"advoost는 우리에게 파트너를 주지 않아"* — 파트너 자격은 **우리가 노력해서 얻을 수 있는 것이 아니다.** §2의 게이트는 조건이 아니라 **벽**이다.

⇒ 이로써 §1~§5의 조사 결과가 하나로 닫힌다:

1. **GFA API는 우리에게 영구히 안 열린다**(Jino 판단, 조사로는 못 뒤집는다)
2. ⇒ **ADVoost는 PAO의 «자동 운영» 대상이 아니다 — 조건부가 아니라 확정이다.** §3의 풍부한 쓰기 표면은 우리에게 존재하지 않는 것과 같다
3. ⇒ 남는 결정은 **둘뿐**이다:
   - **ⓒ 얼마를 태울지** (지출 규모 — 즉시·가역)
   - **ⓔ 어떤 상품을 넣을지** (콘솔 사람 조작 + 우리가 원가 재료 대기)
4. ★그리고 §5의 「입찰은 사람도 못 건드린다」가 **더 이상 결정타가 아니게 된다** — ⓓ가 살아 있을 때만 「넘어도 소용없다」는 논거였고, 이제 그 앞 단계에서 이미 닫혔다. §10의 「§5가 2차 출처 위에 서 있다」는 취약점도 **결론을 흔들지 못한다**(§5가 뒤집혀도 §2 게이트가 그대로 막는다)

⇒ **북극성 ③ *"우리가 운영하는 «모든» 광고 형태"*에 대한 정직한 각주가 하나 생긴다**: ADVoost·GFA 계열(SA의 8.5~13%)은 **「우리가 운영할 수 없는 광고」**로 분류되어야 하고, 「모든」의 분모에서 빠지거나 「닿을 수 없음」으로 명기되어야 한다. 이건 능력 부족이 아니라 **플랫폼이 준 경계**다.

★**이 문서는 광고 전략을 권하지 않는다**(프로젝트 금지선 `no-ad-strategy-recommendations`). 선택지와 그 전제까지가 산출이다.

## §9. [미상] 목록

1. 상품/카탈로그 **단위** include·exclude를 지원하는 API 엔드포인트 — 콘솔엔 있는 듯하나 공개 문서에서 특정 실패
2. ADVoost(SHOPPING objective)가 `adSets/edit` 입찰 파라미터를 **실제로 받는지** — 자동화 전용이라 무시될 가능성, 문서에 명시 없음
3. GFA API 베타 승인 기준·소요 기간·승인율 — 절차만 있고 실적 확인 불가
4. `NAVER_CLIENT_ID`/`SECRET`를 GFA OAuth 앱으로 전용 가능한지 — 현재 네이버쇼핑 API 전용으로 코드에 박힘, 별도 재등록 필요
5. ADVoost가 실제로 쓰는 플랫폼 내부 신호의 구체 — §6-b, 1차 문서 확인 실패
6. GFA 콘솔(사람 UI)에서 노출·클릭·전환을 실제로 볼 수 있는지 — 2차 출처만 존재

## §10. 커버리지 자백

- **1차 출처로 확인한 것**: GFA API 쓰기 표면(§3) · 파트너 게이트 원문(§2) · 우리 코드의 인증·엔드포인트(§1) · prod DB 금액(§7)
- **2차 출처뿐인 것**: ADVoost의 설정 항목 목록 · 「입찰까지 AI가 자동 처리」(§5) · 에셋그룹 상품 필터(§6-d) — **전부 대행사 블로그이고, 네이버 공식 페이지에서 같은 문장을 못 찾았다.** §5는 이 문서의 결정타인데 **2차 출처 위에 서 있다** — 뒤집히면 결론이 「ⓓ의 값어치 하락」 부분까지 함께 흔들린다.
- **안 한 것**: GFA 콘솔 직접 접속 관측 · ADVoost 실패 사례 검색 · 네이버 공식 ADVoost 소개 페이지의 존재 여부 전수 확인
- 「전수 조사 완료」라고 쓰지 않는다.
