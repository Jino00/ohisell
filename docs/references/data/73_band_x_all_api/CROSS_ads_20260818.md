## 0. 재현 방법 (공통)

밴드 CSV를 prod와 로컬 조인하기 위해, prod DB(`ohisell.db`)는 **읽기 전용으로 ATTACH**하고 밴드 CSV만 별도 스크래치 DB에 `.import`했다. prod 쪽 쓰기는 원리적으로 불가능하다(`?mode=ro` + `query_only=ON`).

```bash
# 1) 밴드 CSV를 prod 서버 /tmp로 전송(prod DB 아님, 스크래치 파일)
scp band_group_total.csv sellc.ohitech.co.kr:/tmp/band_group_total_20260818.csv

# 2) 스크래치 sqlite DB에 CSV를 테이블로 적재 + prod를 읽기전용 ATTACH
sqlite3 /tmp/cross_ads_scratch.db <<'SQL'
.mode csv
.import /tmp/band_group_total_20260818.csv band
ATTACH DATABASE 'file:/home/ubuntu/ohisell/backend/ohisell.db?mode=ro' AS prod;
PRAGMA query_only = ON;
SQL

# 3) 이후 모든 질의는 이 스크래치 DB에서 "ATTACH ... ?mode=ro; PRAGMA query_only=ON;" 후 실행
```

이후 각 절의 SQL은 이 상태(스크래치 DB에 `band` 테이블 존재 + `prod.*`가 읽기 전용 ATTACH된 상태)에서 그대로 실행하면 같은 값이 나온다.

### 1-4. ★★복원 가능 창(2,169건) 중 실제로 「제외 전」 daily 행이 존재하는 비율

| restorable_window_rows | matched_with_pre_period_data | 매치율 |
|---|---|---|
| 2,169 | 325 | **15.0%** |

```sql
WITH ex AS (
  SELECT e.adgroup_id, e.search_term, COALESCE(e.console_excluded_at, e.excluded_at) AS excl_ts
  FROM prod.naver_search_term_exclusion e
  WHERE COALESCE(e.console_excluded_at, e.excluded_at) >= '2025-07-23'

SELECT COUNT(*) restorable_window_rows,

    SELECT 1 FROM prod.naver_search_term_daily d
    WHERE d.adgroup_id=ex.adgroup_id AND d.search_term=ex.search_term AND d.ad_date < date(ex.excl_ts)

FROM ex;
```

⚠️ 왜 매치율이 낮은지는 **미상**(원인 미실측) — 후보 가설(제외 당일이 첫 등장일, 텍스트 정규화 차이, WEB_SITE 계열의 낮은 daily 커버리지 등)은 검증하지 않았다. 없는 것을 채우지 않는다.

| band | 복원된 검색어 수 | 그룹수 | 제외 전 비용 | 제외 전 클릭 | 제외 전 전환건수 | 제외 전 전환액 |

```sql
WITH ex AS (
  SELECT e.adgroup_id, e.search_term,
         COALESCE(e.console_excluded_at, e.excluded_at) AS excl_ts
  FROM prod.naver_search_term_exclusion e
  WHERE COALESCE(e.console_excluded_at, e.excluded_at) >= '2025-07-23'

pre AS (
  SELECT ex.adgroup_id, ex.search_term, ex.excl_ts,
         SUM(d.cost) cost, SUM(d.clk) clk,
         SUM(d.conv_purchase_cnt) conv_cnt, SUM(d.conv_purchase_amt) conv_amt
  FROM ex
  JOIN prod.naver_search_term_daily d
    ON d.adgroup_id = ex.adgroup_id AND d.search_term = ex.search_term

  GROUP BY ex.adgroup_id, ex.search_term, ex.excl_ts
)
SELECT COALESCE(b.band,'밴드미부여') band,
  COUNT(*) restored_terms,
  COUNT(DISTINCT pre.adgroup_id) groups,
  SUM(pre.cost) cost_before_exclusion,
  SUM(pre.clk) clk_before_exclusion,
  SUM(pre.conv_cnt) conv_cnt_before_exclusion,
  SUM(pre.conv_amt) conv_amt_before_exclusion
FROM pre LEFT JOIN band b ON b.adgroup_id = pre.adgroup_id
GROUP BY 1 ORDER BY 1;
```

## ② #15 A7 소재 개별입찰·잠금 × 등급 (한정, 횡단면)

\*잠금 행수 합(78+58+180+1+0+0=317) — 인계 수치(317행)와 일치. 개별입찰 행수 합(183+129+248+20+7+1=588) — 인계 수치(588행)와 일치.

```sql
WITH ap AS (
  SELECT adgroup_id,
    COUNT(*) rows_total,
    SUM(CASE WHEN use_group_bid_amt=0 THEN 1 ELSE 0 END) individual_bid_rows,
    SUM(CASE WHEN ad_user_lock=1 THEN 1 ELSE 0 END) locked_rows
  FROM prod.naver_adgroup_product
  GROUP BY adgroup_id
)
SELECT COALESCE(b.band,'밴드미부여') AS band,
  COUNT(DISTINCT ap.adgroup_id) AS groups_with_mapping,
  SUM(ap.rows_total) AS total_product_rows,
  SUM(CASE WHEN ap.individual_bid_rows>0 THEN 1 ELSE 0 END) AS groups_with_individual_bid,
  SUM(ap.individual_bid_rows) AS individual_bid_rows,
  SUM(CASE WHEN ap.locked_rows>0 THEN 1 ELSE 0 END) AS groups_with_lock,
  SUM(ap.locked_rows) AS locked_rows
FROM ap LEFT JOIN band b ON b.adgroup_id=ap.adgroup_id
GROUP BY 1 ORDER BY 1;
```

## ⑤ #22 B4 입찰 변경 이력 × 등급 (기술용)

**원료**: `naver_change_log`의 `action IN ('update_bid','external_bid_change')`. `update_bid` 425행(2026-07-17~07-30), `external_bid_change` 443행(2026-07-22~08-14). `entity_type`별: ad 287·adgroup 150·keyword 431(둘 합계 868 = 425+443).

### 5-1. 부모 롤업 방법 및 성공률 (먼저 확인)

| entity_type | 롤업 방법 | 대상행수 | 롤업 성공 | 롤업 실패 |

| keyword | `naver_entity`(entity_type='keyword').`parent_id` → adgroup_id | 431 | 431 | **0** |

★**중요한 구조 사실**: `naver_entity` 테이블에는 **`entity_type='ad'` 행이 존재하지 않는다**(테이블 전체가 `adgroup`·`campaign`·`keyword` 3종뿐). 그래서 「ad → naver_entity 부모 링크」는 원리적으로 불가능하고, 대신 `naver_adgroup_product.ad_id`(소재 개별입찰 축의 원료, ②와 동일 테이블)를 경유해야 한다 — ref 73 1-A #22의 서술("naver_entity 부모 링크")과 실제 롤업 경로가 ad 축에서는 다르다. keyword는 서술대로 `naver_entity.parent_id`가 adgroup_id를 직접 가리킨다.

```sql
WITH rollup AS (
  SELECT cl.id, cl.action, cl.entity_type, cl.entity_id AS adgroup_id
  FROM prod.naver_change_log cl
  WHERE cl.entity_type='adgroup' AND cl.action IN ('update_bid','external_bid_change')
  UNION ALL
  SELECT cl.id, cl.action, cl.entity_type, ap.adgroup_id
  FROM prod.naver_change_log cl
  LEFT JOIN prod.naver_adgroup_product ap ON ap.ad_id = cl.entity_id
  WHERE cl.entity_type='ad' AND cl.action IN ('update_bid','external_bid_change')
  UNION ALL
  SELECT cl.id, cl.action, cl.entity_type, ne.parent_id AS adgroup_id
  FROM prod.naver_change_log cl
  LEFT JOIN prod.naver_entity ne ON ne.entity_type='keyword' AND ne.entity_id = cl.entity_id
  WHERE cl.entity_type='keyword' AND cl.action IN ('update_bid','external_bid_change')
)
SELECT COALESCE(b.band, CASE WHEN r.adgroup_id IS NULL THEN '롤업실패' ELSE '밴드미부여' END) AS band,
  r.action,
  COUNT(*) AS rows
FROM rollup r LEFT JOIN band b ON b.adgroup_id = r.adgroup_id
GROUP BY 1,2 ORDER BY 1,2;
```

### ⑤ 제약 각주
- **인과 오염 축 — 경향판정 금지**(ref 59 §3-5, line 150: "직접 레버지만 인과 오염이 가장 심한 축(성과를 보고 입찰을 바꾼 이력 = 역인과가 기본값)이라 경향 판정엔 안 쓴다"). 위 표는 「어느 밴드에서 입찰 변경이 얼마나 있었나」의 **기술(記述)**일 뿐, 「입찰 변경이 밴드를 만들었다/구했다」로 읽지 않는다.
- `update_bid`(2026-07-17~07-30, 14일)와 `external_bid_change`(2026-07-22~08-14, 24일)는 **창이 다르다** — 5-2 표를 action별로 분리한 이유. 두 action을 밴드별로 단순 합산하면 서로 다른 창의 숫자를 섞게 된다.
- band2의 external_bid_change(237)가 update_bid(90)보다 두드러지게 많다 — [산술] 관측이며 원인(외부 변경이 band2에 집중된 이유)은 실측하지 않았다(미상).
