## §9. 이 표를 다시 재는 법

```bash
# ① 대기 구성
SELECT proposal_type, COUNT(*) FROM naver_proposals WHERE status='pending' GROUP BY 1 ORDER BY 2 DESC;
# ② 승인이 병목인가 (최근 창으로 — 전 기간으로 재면 과거 잔여가 섞인다)
SELECT date(created_at), COUNT(*), SUM(executed_change_log_id IS NOT NULL)
  FROM naver_proposals WHERE status='approved' AND created_at >= date('now','-3 day') GROUP BY 1;
# ③ 차단 사유 버킷 (rationale 문자열 매칭 — 사유문이 바뀌면 버킷이 샌다)
SELECT CASE WHEN rationale LIKE '%스코프 밖%' THEN 'A' WHEN rationale LIKE '%bleeding%' THEN 'B'
            WHEN rationale LIKE '%쿨다운%' THEN 'C' WHEN rationale LIKE '%가드레일%' THEN 'D'
            ELSE 'E' END, COUNT(*)
  FROM ops_diary_entries WHERE event_type='blocked' AND created_at >= date('now','-3 day') GROUP BY 1;
# ④ 관할 vs 문 앞
SELECT COUNT(*) FROM naver_adgroup_scope WHERE enabled=1;
SELECT COUNT(DISTINCT adgroup_id) FROM ops_diary_entries
  WHERE event_type='blocked' AND rationale LIKE '%스코프 밖%' AND created_at >= date('now','-3 day');
```

★**③은 사유 «문자열»에 의존한다** — 사유문을 고치면 버킷이 조용히 샌다.
이 저장소는 09-05에 정확히 그 사고를 겪었다(적대 리뷰 P1-1: 새 사유문이 `classify_hold_reason` needle을 잃어
버킷이 `bleeding`→`daily_loss`로 이동, 「1,761→0」이 «열려서»인지 «이름만 바뀌어서»인지 구분 불가).
