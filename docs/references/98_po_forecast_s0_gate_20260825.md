## 1. S0-a — 발주서조회는 품목 라인을 주지 않는다 ❌

### 관측
대상 파일: `AI_office/data/ecount_migration/src_purchase_orders.jsonl` (1,622건, `ORD_DATE` 2016-02-23~2026-08-24)

| 검사 | 결과 |
|---|---|
| `(ORD_DATE, ORD_NO)` 중복 | **0** ⇒ 1행 = 발주서 1건(헤더) |
| 응답 필드 41개 중 `PROD_CD`(품목코드) | **없음** |
| `PROD_DES` 「… 외 N건」 패턴 | **1,273건 (78.5%)** |

`QTY`·`BUY_AMT`는 **그 발주서 전체 라인의 합계**다.

### 역파싱 불가 (실증)

**단일품목 발주서 349건(21.5%)만 유효**하다 — 단 `PROD_DES`가 `PROD_CD`가 아니라 자유텍스트라 품목마스터 매칭이 별도로 필요하고, 그건 미검증이다.

### 두 번째 제약 — 실서버가 거부한다
> "ECOUNT는 API를 하나씩 «검증»해야 열린다. 검증된 API는 **8개뿐**이고 **발주서조회/입력은 목록에 없다.** 실서버는 `EXP00001 인증되지 않은 API입니다`, **테스트 엔드포인트는 200으로 실데이터를 준다.**"
> — `AI_office/.claude/memory/HANDOFF_ecount-n9-*_20260824.md`

확보된 1,622건은 **테스트존(sboapi) 산출물**이다(`_meta.endpoint: "test"`). 실서버 경로는 ECOUNT에 검증 신청을 해야 열린다. **두 존의 산출값 대조는 실서버가 아예 거부라 원리적으로 불가능**한 상태다.

## 7. ★예약 잔량 — 두 방법의 4,100 갭을 완전 분해

```
4,100 = 900   (2025년 백로그 — 발주 원장을 14건까지 물려 잡은 몫)
      + 1,950 (0708-1 회계시차)
      + 1,250 (미상, 5개 PO에 분산 · 0617-1은 −200 상쇄)
```

### 정본 = 발주번호 직접 연결 (**16,100개**)
FIFO는 **12,000**(2026만) → **12,350**(+2025년 4건) → **12,900**(+2025년 14건). 입력을 3배 넓혀도 **22%만 해소**.

### ★스모킹건 — 0708-1
- `2026-08-19` ECOUNT 매입확정 1,350개 ↔ `08-18` 통관 1,350개 → **1일 시차, 정확 대응(정상)**
- `2026-08-03` ECOUNT 매입확정 **2,350개** ↔ **대응하는 통관신고 없음** → FIFO가 물리적 입고로 오인

⇒ **ECOUNT 매입확정 ≠ 세관 통관.** 회계 이벤트가 통관보다 먼저(때론 몇 주) 잡힌다.

### ★입력범위 가설의 반증
