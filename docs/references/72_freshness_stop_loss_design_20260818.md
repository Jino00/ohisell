## 1. ★핵심 원리 — 상한 프록시는 «0» 쪽에서만 결정적이다

스마트스토어 매출은 **광고 귀속 매출의 상한**이다. 그러므로 **상한이 0이면 참값도 0**이다 — 추정이 아니라 산술이다. 반대로 상한이 양수인 것은 광고가 벌었다는 증거가 **되지 못한다**.

| 판정 형태 | 성립 | 근거 |
|---|---|---|
| **손절 게이트**(비용 급증 ∧ 당일 매출 상한=0 → 되돌림) | ✅ **결정적으로 성립** | 상한=0 ⇒ 광고 전환=0. **귀속이 필요 없다** — §0-B의 부정 결과가 이 판정을 훼손하지 않는다 |
| 소진 속도 이상 감지(시간대별 광고비만) | ✅ 성립 | 매출 자체가 불필요 |
| 168칸 비용×매출 분포 대조 | ⚠️ **측정으로만** | 「광고 전환이 전체 매출의 시간 분포를 따른다」는 **미검증 가정**이 낀다 → 자동 집행 근거 불가, 관측·보고까지 |
| 「이 시간대가 효율적 → 입찰 올려」 | ❌ **불성립** | 확장 판정은 상한이 아니라 **귀속(폭)**이 필요하다. §0-B가 막은 것이 정확히 이것 |
| 같은 시각 비용↔매출 대응 | ❌ 불성립 | `order_date`는 **결제 시각**이고 클릭은 그보다 앞선다 — 시차 `[미상]`, 시간 단위 인과 대응은 원리적으로 오염 |

★**한 줄**: 시간축은 프록시의 **«폭»(귀속)을 못 좁히고 «지연»만 좁힌다.** 그리고 지연 단축이 총이익에 기여하는 자리는 정확히 **손절(출혈 차단)** 방향이다 — 확장은 폭이 필요하고, 정지는 **신선한 0**이면 충분하다. 45분 크론이 이미 그 신선도를 나르므로 이 설계는 **새 수집이 아니라 읽기 배선**이다.

**방지할 착각 3**: ①상한>0을 「광고가 번다」로 읽기(확장 오용) ②시각 대응을 인과로 읽기 ③**1:1 매핑이 아닌 그룹에서 프록시가 헐거워짐** — 여러 상품이 섞이면 상한=0이 잘 안 떠 게이트가 **덜 발화**한다. ★위험 방향이 **출혈을 놓치는 쪽**이고 오발 정지가 아니라는 **비대칭을 명시하고 감수**한다.

★**기존 배선 4곳(§0-D)도 재감사 대상이다** — 프록시를 «확장 방향»으로 쓰는 곳이 있으면 오늘 결함과 같은 급의 불건전. `[미상 — 4곳의 사용 방향을 읽으면 확인된다(읽기 전용, 반나절 미만)]`

### ① `probe_revert._conv_direct_today` 수리 (C-1 + C-2를 한 PR로) — **최우선**
- **무엇**: **2신호 2단 판정**으로 교체. 주신호 = `NaverAdgroupHourlyToday`(당일 광고그룹 전환 — **소비처 0곳이던 것을 여기 배선**, 광고 귀속 신호다) · 보강 = 1:1 매핑 상품의 당일 매출(`_one_to_one_product` **이미 있는데 안 쓰는 헬퍼** + `Order.order_date`). 어휘 2단화: **확정 0**(상품 매출도 0 — 산술적 확실) / **잠정 0**(네이버 전환 0인데 상품은 팔림 — 당일 집계 지연에 의한 거짓 0 가능, **다음 시간 재확인 후 발화**).
- **박힌 잘못된 전제**: 「`naver_ad_daily`에 오늘이 있다」 → 매시간 도는 밸브의 「오늘 전환 0」 조건이 **항상 참**이었다.
- **라이브 합격**: 배포 후 `run_bleed_valve` 로그(KST)에서 `NaverAdgroupHourlyToday`에 당일 전환이 실재하는 그룹의 `conv_direct_today`가 **0이 아닌 값**으로 관측 + **구경로/신경로 1회 병기 로그**(구=0·신>0 대조). 판정 근거 테이블·시각을 로그에 남긴다.
- **선행**: 배포 필요(safe_deploy) · Jino 결정 **불요**(결함 수리) · 판정 코드라 **PR 경계 적대 리뷰 의무**(§4).
- ★**`optimizer` 해제 결정보다 먼저 끝나야 한다** — 지금은 완전 정지라 밸브가 되돌릴 실집행이 없어 **배포 위험이 최저**이고, 해제 순간부터 이 밸브가 **유일한 시간 단위 안전장치**다. **고장 난 밸브 위에서 해제하면 안 된다.**
- **위험**: `NaverAdgroupHourlyToday`의 당일 갱신 주기·전환 지연계상 크기 `[미상 — 수집 시각 분포와 D−1 확정치 대비 당일 누적치를 하루치 대조하면 확인]`. 지연이 크면 「잠정 0」 오발 → **2단 판정이 그 위험을 흡수하는 장치**다.

### 부류ⅰ. 적재 창 밖을 읽는 판정
| 후보 | 판정 | 이유 |
|---|---|---|

| ★**`safe_deploy.sh` 정적 가드** | **채택 — 속효층** | **배포가 이 repo의 실제 초크포인트**다(CI 부재의 대체). 「날짜 컬럼과 오늘의 직접 비교」 패턴 grep + 허용목록 — 해당 리터럴이 **코드 전체 1곳뿐**이라 초기 허용목록이 짧다 |
| 적대 리뷰 체크리스트 1줄 | 채택 — 일반화층 | 「판정 함수의 각 입력에 **적재 창을 명시**했는가」 |

### 부류ⅱ. 이미 있는데 잊는 데이터
(hour 필드 미독 · `NaverAdgroupHourlyToday` 소비처 0 · 헬퍼 미사용) — grep 한 줄로 못 막는다. **예방이 아니라 «발견»의 문제**다.
→ 집행 지점 = **주기 구조 감사에 기계 항목 추가**: 「**writer는 있는데 reader가 0인** 테이블/필드 인벤토리」(소비처 카운트는 grep으로 기계 산출 가능). **이번에 셋 다 정확히 이 모양**이었다 — 매주 이 표를 뽑으면 «잊음»이 **7일 이상 못 산다**.

### 위키 승격 (패턴 1개)
**「판정 입력에는 적재 창을 물어라 — 상한 프록시는 0쪽에서만 결정적이다」**, `enforcement:` = 읽기 헬퍼 + `safe_deploy` 가드 + 감사 인벤토리 항목 **셋을 지목**. 관련 파일이 0개인 현 상태에서 이것이 **첫 집행 지점 보유 패턴**이 된다.
