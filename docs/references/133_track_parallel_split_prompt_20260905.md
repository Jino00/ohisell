## Part A — 트랙을 쪼개라고 시킬 때 붙여넣는 프롬프트

```
`<트랙파일>` 트랙의 남은 일을 병렬 세션으로 쪼개는 계획을 세워 줘.

## 왜 이 순서인가 (먼저 읽어라)
지난번에 재기 «전에» 나눠서 「병목은 하나」라고 틀렸다. 분류가 틀리면 그 뒤 작업이 전부
헛돈다. 그래서 아래는 «측정 → 분류 → 배분» 순서이고, 각 단계의 관측값을 숫자로 보여준 다음
다음 단계로 가라. 중간 결과를 내가 보고 방향을 바꿀 수 있어야 한다.

## 조사하기 전에 답하지 마라
파일을 열지 않고 코드에 대해 단정하지 마라. 트랙·census 문서를 언급하면 반드시 읽고 답하라.
확실하지 않으면 **「모른다」·「판정불능」이라고 쓰는 것이 옳은 답**이다 — 추측으로 채우면
그 위에 세운 배분이 전부 틀어진다. 추측은 🧠로 표시해 실측과 분리하라.

## 1단계 — 병렬이 정말 병목을 푸는지부터 재라
다음을 실제로 실행해 숫자를 보여라:
- 최근 14일 머지된 PR 수
- 같은 기간 이 트랙 진행률(N/M) 변화
**왜**: PR은 많은데 진행률이 안 움직였다면 처리량은 병목이 아니다. 그러면 세션을 늘려도 같은
결과가 나온다. 그 경우 「병렬이 아니라 순서·범위가 문제」라고 먼저 말하고 나에게 물어라.

## 2단계 — 남은 일을 전수로 세라
트랙 헤더의 미체크 `합격:` 항목 + 관련 census/기능 전수 문서를 **전부 읽어라**.
각 항목에 **마지막 측정일**을 붙이고, 2주 넘은 값은 「낡음」으로 표시하라.
그리고 각 항목을 셋 중 하나로 판정하라:
  ① 이미 조사가 끝났다(바로 만들 수 있다)  ② 더 재야 한다  ③ 원리적으로 불가하다
**왜**: 목록이 여럿이면 어느 것도 단독으로 현재를 못 말한다. 지난번에 목록의 「왜」 열이
틀린 채로 작업할 뻔했고, 3개 항목이 각각 다른 이유로 막혀 있었다.

## 3단계 — 주제가 아니라 «파일»로 잘라라
각 항목이 어느 파일을 고쳐야 하는지 grep으로 확인하고 그 파일들의 줄 수를 재라.
결과를 이 표로 내라:
  | 덩어리 | 항목 | 독점 파일 | 병렬 가능? |
**왜**: 여러 항목이 같은 큰 파일에 몰리면 그 항목들은 한 세션이다. 나누면 서로 덮어쓴다.
지난번에 13개 항목이 7,900줄짜리 파일 하나에 몰려 있었다.

## 4단계 — 조사만 돌리면 진행률이 0인 것을 말하라
조사 세션은 코드 0줄이고, 그러면 진행률도 0줄이다. 2단계에서 ①로 분류한 항목이 있으면
**조사와 동시에** 돌리자고 제안하라. 특히 **지금 이미 값(돈·시간)을 치르고 있는 항목**을
찾아 우선순위를 매겨라.
**왜**: 이 저장소의 상습 실패 모드가 「발견이 처분 없이 이월만 된다」이다.

## 5단계 — 세션별 착수 지시문을 써라
새 세션은 이 대화를 못 본다. Part B 템플릿의 «모든» 칸을 채워라.

## 6단계 — 내가 열어야 하는 것을 가려라
- **서브에이전트로 가능**: 병렬로 돌고, 격리된 컨텍스트가 필요하고, 상태를 공유하지 않는
  독립 작업 — 대개 읽기 전용 조사
- **사람 세션이어야 함**: 승인 지점이 있는 것(계약 승인·되돌릴 수 없는 액션), 판정문을
  받아야 하는 것(적대 리뷰·완료 QA)
**왜**: 서브에이전트는 내 승인을 못 받는다. 네가 대신 승인하면 그건 자기승인이다.
단순하거나 순차적인 일, 단일 파일 수정은 위임하지 말고 직접 해라.

## 산출
1단계~4단계의 관측 표들 → 5단계 지시문 초안 → 6단계 구분. 그다음 내 결정을 기다려라.
```

## Part B — 세션 착수 지시문 템플릿 (각 세션에 붙여넣는 것)

각 칸을 채운다. **빈칸을 남기지 마라 — 새 세션은 이 대화를 못 본다.**

```
## 목표
<Jino 원문 그대로. 각색 금지. 없으면 트랙 헤더 `목표:` 인용>

## 왜 지금 (실측 한 줄)
<「X가 N일째 멈춰 있다」 · 「하루 M원이 샌다」 — 숫자가 있는 문장>

## 할 것
<번호 목록. 완성 상태를 문장으로. 예: "① 리셋 API 신설 ② 화면 버튼 ③ 감사 기록">

## 이 세션만 쓰는 파일 (독점)
<경로 나열>

## 다른 세션이 쓰는 중이라 열지 않는다
<경로 나열> — 지금 <세션명>이 동시에 고치고 있어 열면 서로 덮어쓴다

## 합격기준 (라이브 증거 체크박스)
- [ ] <표면을 지목해서. 「X가 계산된다」가 아니라 「화면 어디에 뜬다」>
- [ ] <조사 세션이면: `git diff --stat origin/main -- backend/ frontend/ | wc -l` → 0>

## 검증 명령 (한 줄)
<★받는 쪽이 앉아 있는 위치에서 도는지 «직접 실행해 보고» 쓸 것>

## 절차
<S/M/L 판정 + 그에 붙는 절차. L이면 계약 1장 → Jino 승인 1회 → 구현 → 적대 리뷰 → QA>

## 범위 규율
직접 요청된 것과 명백히 필요한 것만 한다. 요청 밖의 기능 추가·리팩터·「개선」은 하지 않는다.
버그 수정에 주변 정리를 얹지 않고, 한 번 쓰는 것에 헬퍼·추상화를 만들지 않는다.
안 고친 코드에 주석·타입을 덧붙이지 않는다.
**왜**: 병렬 세션이라 범위를 넘으면 남의 파일에 닿고, 그 순간 충돌한다.

## 되돌릴 수 있는 것과 없는 것
파일 편집·테스트 실행처럼 로컬에서 되돌릴 수 있는 일은 묻지 말고 해라.
되돌리기 어렵거나 공유 시스템에 닿거나 파괴적인 일은 **먼저 물어라**:
  · 파괴적 — 파일·브랜치 삭제, DB 테이블 드롭
  · 되돌리기 어려움 — force-push, `git reset --hard`, 게시된 커밋 수정
  · 남에게 보이는 것 — push, PR 코멘트, 메시지 발송, 공유 인프라 변경, prod 배포, 외부 API 쓰기
막혔을 때 파괴적 수단을 지름길로 쓰지 마라(`--no-verify`로 검사 우회, 남의 작업일 수 있는
낯선 파일 버리기 금지).

## 테스트를 통과시키는 것이 목적이 아니다
모든 유효한 입력에 맞는 일반 해를 써라. 테스트 케이스에만 맞는 값을 박아 넣지 마라.
테스트는 정확성을 «확인»하는 것이지 해답을 «정의»하는 것이 아니다.
과제가 불합리하거나 테스트가 틀렸다고 판단되면, 우회하지 말고 나에게 말해라.

## 조사하기 전에 답하지 마라
열지 않은 파일에 대해 추측하지 마라. 특정 파일이 언급되면 반드시 읽고 답해라.
확실하지 않으면 「모른다」·「미상」이라고 쓰는 것이 옳다.

## 임시 파일
반복용 임시 스크립트를 만들었으면 끝에 지워라.

## 상태 기록 (컨텍스트가 바뀌어도 이어지도록)
· 구조화된 상태(테스트 결과·항목 상태)는 JSON으로
· 진행 메모는 자유 텍스트로
· git 커밋 메시지에 «무엇을 왜»를 남겨라 — 다음 세션이 그걸로 상태를 복원한다
컨텍스트가 한계에 가까워져도 작업을 임의로 중단하지 마라. 진행 상태를 파일과 커밋에 저장한
다음 이어가라.

## 보고 형식
<「관측(창·분모·측정일) → 판정 → 근거 좌표」 / 발견 3~5개 / 추측은 🧠 / 마지막에 PR 번호·
 머지 여부·`git status --short`>

## 이 저장소의 함정 (그대로 복사)
1. 체인: `chain.sh open`은 마지막 행이 열려 있으면 거부한다 — 새 체인을 신설하라
2. 공유 메인 폴더에서 `git worktree add`는 mmap 오류로 죽고, 그 폴더는 origin/main보다
   1,250커밋+ 낡았다 → `git clone --depth 1 --branch main <repo> <경로>`
3. 트랙 `확인:` 줄은 모든 세션이 같은 자리에 쓴다 — 각자 PR로 내고 순차 머지
4. 머지: `MERGE_WAIT=1800 bash scripts/safe_merge.sh <PR>` · `--force` 금지
   (「체크 0건」은 초록이 아니라 CI 미등록이니 잠시 뒤 재시도)
5. 배포: `scripts/safe_deploy.sh` · 커밋은 경로 지정(`git add -A` 금지)
6. prod 조회: 스크립트를 파일로 만들어 scp 후 stdin(인라인 heredoc은 따옴표가 벗겨진다).
   ssh 출력을 `head`로 자르지 마라 — 행을 놓쳐 오탐이 난다
```

## Part D — v1에서 무엇을 왜 고쳤나 (공식 권고 대비)

| 공식 권고 | v1의 문제 | v2에서 한 것 |
|---|---|---|
| **지시마다 «왜»를 붙여라** — 모델이 의도를 일반화한다 | 단계만 나열하고 이유가 없었다 | 6단계 전부에 **왜** 한 줄 |
| **할 것을 말하라, 하지 말 것 말고** | 「안 함」이 대부분이었다 | **「할 것」을 먼저**, 「안 함」은 남기되 각각에 이유 |
| **예시가 형식을 가장 확실히 조종한다** | 예시가 0개 | **Part C 채워진 예시** 추가 |
| **불확실성 표현을 허용하라** — 환각이 준다 | 없었다 | 「모른다·판정불능이 옳은 답」 명시 |
| **조사 전에 답하지 마라** | 없었다 | 본체·템플릿 양쪽에 넣음 |
| **되돌릴 수 있는 것/없는 것 구분** | 「배포는 safe_deploy」 정도 | 공식 샘플대로 **범주와 예시**로 |
| **과설계 방지** | 「리팩터 금지」 한 줄 | 범위 규율 문단(주석·방어코딩·추상화까지) |
| **테스트 통과가 목적이 아니다** | 없었다 | 문단 추가 |
| **서브에이전트 판단 기준** | 「읽기 전용이면 OK」 | 공식 기준(병렬·격리 컨텍스트·독립 작업) + **단순·순차·단일파일은 직접** |
| **상태를 파일·git으로 이어라** | 없었다 | JSON=구조·텍스트=진행·git=상태 |
| **컨텍스트는 유한 자원** | 지시문이 길어지는 것을 안 막았다 | 템플릿을 칸으로 고정해 길이 통제 |
| **XML 태그는 아주 복잡할 때만** | 안 씀 | 그대로 — 제목·여백으로 충분 |

★ 한 가지는 **일부러 안 따랐다**: 「안 함을 쓰지 마라」. 이 저장소의 계약 규격이 `안 함:`을
필수 요소로 두고, 병렬 세션에서는 **경계를 이름으로 못 박는 것**이 충돌을 막는 유일한 수단이다.
대신 공식 권고대로 **「할 것」을 먼저 두고 「안 함」마다 이유를 붙였다.**

| 테스트 통과가 목적이 아님 | — | ★넣음 |

## ★테스트를 통과시키는 것이 목적이 아니다 (이 세션에 특히 해당)
앞선 지시문이 「표본 하한 게이트 테스트 43개 유지」를 합격기준으로 걸었다. 그건 **깨지 말라는
뜻이지 초록을 만들라는 뜻이 아니다.**
· 모든 유효한 입력에 맞는 일반 해를 써라. 테스트 케이스에만 맞는 값을 박아 넣지 마라
· 테스트는 정확성을 «확인»하는 것이지 해답을 «정의»하는 것이 아니다
· 테스트를 지우거나 고쳐서 통과시키지 마라 — 기능이 조용히 사라진다
· 과제가 불합리하거나 테스트가 틀렸다고 판단되면 **우회하지 말고 그렇게 말해라**
왜: 이 저장소에서 「라벨은 붙고 집행은 안 됨」이 반복 실패 모드다. 진동 차단은 «수를 줄이면»
초록이 되는 종류의 일이라 특히 위험하다.

것이 옳은 답이다. 추측은 🧠로 표시해 실측과 분리하라.

· 진동 차단에 필요 없는 리팩터·정리를 얹지 마라
· 한 번 쓰는 것에 헬퍼·추상화를 만들지 마라
· 「나중을 위한」 설정 가능성을 더하지 마라
왜: B1이 같은 시각에 인접 파일을 고치고 있고, 오늘 09:12에 배포된 D-NAO-286이 이 파일들에
