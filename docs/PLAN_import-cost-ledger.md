## 1. 목표 / 이번에 안 하는 것

**누가 뭘 못하나.** 수입 실제 원가가 어디에도 없다. 통관 서류 3종(CI·PL·통관경비서)은 파일로만
존재하고, 거기 적힌 실제 환율·실제 관세·실제 운임이 원가에 반영되지 않는다. 지금 원가는 엑셀의
하드코딩 계수(환율 200·물류 10%·관세 5.6%)로 «만들어진» 값이고, 8/18 실건과 대조해 보니 계수 셋이
전부 어긋나 있었다(각각 −4.9% / +2.0%p / +0.47%p) — 상쇄되어 합계는 +3.4%에 그쳤을 뿐이다.

**되면 뭐가 달라지나.** 수입 1건의 서류 3종을 넣으면 ①3중 검산 통과 ②통관비의 SKU별 배부
③**라인별 실제 단가(VAT 포함/제외 두 값)**가 저장·조회된다. 표준원가(엑셀)와 나란히 놓여
「계수가 얼마나 벗어났나」가 보인다.

## 2. 판단기준

1. **항상 기본 표시는 VAT 포함 단가다.** 왜냐하면 손익 엔진 전 축이 D-NAO-150(Jino 원문
   *"Sellc에 들어있는 원가는 부가세 포함된 가격이야."*)으로 통일돼 있고 `payable_vat()`가
   매출VAT−매입세액을 순이익에서 한 번 상쇄한다 — 제외를 기본으로 두면 승인된 결정과 충돌한다.
2. **항상 두 값(포함·제외)을 계산 시점에 확정 저장한다.** 왜냐하면 원가 정의가 나중에 바뀌어도
   재파싱 없이 표시만 바꾸면 되고, 값이 «계산 시점에 확정된 숫자»로 남아 소급 오염이 없다.
3. **배부는 항상 금액(인보이스 가액) 기준이다.** 왜냐하면 관세가 가액 비례로 매겨져 성격이 맞고,
   중량·부피 기준과 0.3% 이내로 수렴하며, 수량 기준만 부자재가 통관비의 59%를 흡수해 왜곡된다.
4. **정본은 항상 사람이 확인한 폼 데이터다 — 파싱은 채워주기 편의다.** 왜냐하면 서류 양식
   동일성이 미확인이라(1회분만 봄) 파서 실패가 시스템 실패가 되면 안 된다. 라인 분류
   (판매 SKU / 부자재)도 같은 원칙 — 매핑되면 자동 제안하되 확정은 사람이 한다.
5. **항상 «Σ배부 = 배부대상 총액(미배분 잔액 0)»을 화면 안 검산으로 낸다.** 왜냐하면 2026-08-19
   광고비 배분 사고(교훈 #327)가 «원장 기준으로 세다가 증발»이었고, 검산을 화면 밖에 두면
   아무도 안 본다.
6. **환율은 항상 통관경비서의 신고환율을 쓴다(8/18 건 = 209.88).** 왜냐하면 과세금액÷INV로
   역산한 210.50과 0.3% 어긋나는데 원인이 확인 안 됐고, 둘 중 하나를 못 박지 않으면 합격기준
   판정이 결정적이지 않다.

## 3. 금지선

- **`product_master.cost_price` 컬럼과 그 소비처 14곳을 한 줄도 건드리지 않는다.** 순수 추가만.
- **검산 3종을 통과하지 못한 건을 「확정」 상태로 저장하지 않는다.**
- **「부가세 제외가 회계 정답」을 화면·문서에 확정 기재하지 않는다** — 법인세법 시행령 제72조에
  「부가가치세」·「매입세액」·「관세」라는 단어가 없음을 조문 원문으로 확인했다. 세무사 확인 전까지 보류.
- **원본 서류 파일을 보관하지 않고 저장하지 않는다** (근거 보존).
- **DB 스키마 변경이므로 `scripts/safe_deploy.sh --migrate` 순서 강제** — 이 앱은 부팅 시
  인프로세스 마이그레이션을 하지 않는다.
- **PR 경계 적대 리뷰 1회 없이 닫지 않는다** — DB 스키마 변경이라 면제 없음. 재현 요구 + 변이 주입 포함.
- D-CPP·교훈 번호는 `scripts/next_ids.sh`로만 받는다.

## 4. 합격기준 — 라이브 증거 시나리오

「테스트 통과」·「코드 존재」는 합격이 아니다. **prod에서 관측**되어야 한다.
시나리오: prod 화면에서 8/18 실건 서류 3종을 입력하고 확정한다. 그 뒤 —

1. **검산 3종 통과가 화면에 표시된다**: ①CI 수량합 = PL 수량합 (SKU별, 라인 분해가 달라도 합으로)
   ②CI 총액 = 경비서 INV Value (CNY 23,100) ③Σ배부액 = 배부대상 총액, **미배분 잔액 0원**.
2. **`Glass_Ip17Pro` 500개의 단가가 3,201원(VAT 포함) / 2,910원(VAT 제외)으로 관측된다**
   (환율 209.88 기준, 금액 배부). 소수 반올림 ±1원 허용.
3. **`cleaning kits` 2,400개가 `line_type='material'`(부자재)로 저장되고 배부액 54,992원이 관측된다.**
   > ★**정정 (2026-08-22, 착수 직후·구현 전)**: 승인 시점 계약서엔 **54,993원**으로 적혀 있었다.
   > 실제는 `661,620 × 1920/23100 = 54,991.79` → 최대잔여법으로 **54,992원**이다.
   > 기획 단계의 반올림 오기이고, **미달 판정 뒤의 기준 완화가 아니다**(구현 전에 발견).
   > ⓑ의 2,910/3,201도 정확히는 **2,909.96 / 3,200.96**이라 ±1원 허용 안에 든다.
4. **입력 전후로 `product_master.cost_price`의 SELECT 결과가 완전히 동일하다**(변화 0건).
   순수 추가라는 증거 — 배포 전후 캡처를 대조한다.
5. **원본 서류 파일 3개가 그 수입건에서 다운로드된다.**
6. 배포 직후 `GET /api/scheduler/health`의 기존 필드(`cost_drift` 포함)가 배포 전과 동일하다.
