## §0. 이 계약이 사는 이유 — 정직한 논증 (약하면 약하다고 적는다)

**기대치부터 낮춘다.** 75건 전건 개봉(08-19)에서 **층화 가용 0건**이 나왔다. 상품 도메인 64 endpoint 전체에 변경-피드·변경 타임스탬프가 없다(개봉 실측 — 매트릭스 개정 9 확정). 즉 C10을 적재해도 얻는 것은 **「현재 단면」이지 시계열이 아니고**, 시계열은 폴링을 시작한 날부터만 쌓인다. 이 축이 내일 당장 밴드 연관(A/B)을 낳을 가능성은 낮다.

그럼에도 사는 이유 4개 — 강한 순서대로, 강도 자백 병기:

1. **[강함] 소급 불가 축의 «창을 여는 것» 자체가 산출물이다.** 가격·재고·판매상태·카테고리의 변경 이력은 어디에도 저장돼 있지 않고, API가 과거를 주지 않으므로 **폴링 개통일 = 관측 창의 시작일**이다(검색량 기준선 D-NAO-186과 같은 성질). 늦게 열수록 창이 영원히 짧다. 나중에 「가격 변경이 밴드 이동에 선행하는가」를 물으려면 지금 열어야 한다.
2. **[강함] 인계 [미상] 1건의 첫 정량화 기회.** `channelProductId ≡ naver_adgroup_product.mall_product_id` 동일성은 [미상]인 채 코드가 이미 전제로 조인 중이다(`models.py:2346` 주석 — 이번에 코드로 재확인). C10 적재분과 `mall_product_id`의 **조인율 실측**이 이 계약의 합격기준 ⓒ에 들어 있다 — 동일성 확정은 아니어도(교집합은 인과가 아니다) 커버리지 %가 처음 숫자로 남는다.
3. **[중간] M1 마감 = 북극성 §6 표의 항목.** 진도 4/5가 이 축 하나로 고착돼 있다. 「완료 ≠ 모든 데이터」 병기 규율(D-NAO-200) 하에서의 마감이다.
4. **[약함 — 확인 전엔 팔지 않는다] 시간가변 신호 후보.** `orderType` enum에 `POPULARITY`·`ACCUMULATE_SALE`·`TOTAL_REVIEW_COUNT`·`AVERAGE_REVIEW_SCORE`가 있어(공식 문서, 08-20 직취) 응답에 누적판매·리뷰 필드가 실릴 **가능성**이 있다. 실리면 일일 폴링이 진짜 시계열(리뷰 증가율 등)을 낳는다. 단 응답 스키마의 `channelProducts` 하위가 문서에서 생략돼 있어 **[미상]** — §8 첫 확인 항목. 이 항목을 근거로 승인하지 말 것.

**기각(안 함) 선택지 — Jino가 고를 수 있게**: 기각하면 API 콜 0·디스크 0·구현 세션 1회 절약. 잃는 것은 위 1(창 개통 지연 — 하루 미룰 때마다 창이 하루 짧아진다), 2(조인율 실측 기회), 3(M1 4/5 고착). **즉효 분석 가치가 낮은 것은 사실**이므로 「지금 말고 M2 뒤」도 합리적 선택이다 — 단 그 경우에도 1의 성질(소급 불가) 때문에 미루는 날수만큼 창을 잃는다는 것만 알고 고르면 된다.

## §2. 판단기준 (항상 A, 왜냐하면)

1. **항상 조회 전용 표면만 쓴다**, 왜냐하면 상품 도메인 21개 쓰기 endpoint는 실판매 상품을 실변경하며 이 계약의 목적은 관측이지 조작이 아니기 때문이다.
2. **항상 전건 폴링을 기본 경로로 하고 서버측 기간 필터(`periodType=PROD_MOD_DAY`)는 보조 검증으로만 쓴다**, 왜냐하면 카탈로그가 1,000 안팎(prod 실측 08-20: `naver_product_bep` 758행 · adgroup_product distinct 702)이라 전건이 폴링 1회당 2~3콜로 충분히 싸고, `modifiedDate` 갱신 의미론(어떤 변경이 이 값을 전진시키는가)이 [미상]이라 필터 의존은 조용한 유실(교훈 #319의 부류 — 정상 응답의 일부로 오는 절단)을 낳을 수 있기 때문이다.
3. **항상 페이지 완주를 `totalPages`/`last`로 판정하고 미완주를 표면화한다**, 왜냐하면 이 repo는 절단이 `success`로 기록된 실사고(교훈 #319·#320)를 갖고 있고, 「완주」를 주장하는 필드를 넣으면 그 함수의 모든 조용한 실패 경로를 같은 턴에 훑어야 하기 때문이다.
4. **항상 변경 이력은 변경분만 적재하고 현재 단면은 1벌만 유지한다**, 왜냐하면 prod 디스크가 93%(여유 7.1G, 08-20 09:3x 실측)이고, 전건 일일 스냅샷은 D-NAO-198 실측(98.2%가 퇴화 행)이 기각해 둔 설계이기 때문이다.
5. **항상 필드를 버릴 땐 이 계약에 명시하고, 현재 단면엔 응답 원문(raw JSON)을 함께 보존한다**, 왜냐하면 grain·필드 절삭은 로컬 결정이 아니고(교훈 #315 — 내 절삭이 원격 전제를 깬 실사고), 응답 스키마의 하위 구조가 문서에서 생략돼 있어 지금은 전체 필드 목록조차 [미상]이기 때문이다.
6. **항상 숫자엔 창·자·측정일을 병기한다**(D-NAO-206), 왜냐하면 이 트랙은 표본값(533)이 전수값(1,013)과 20%p 어긋난 전례(A6)를 갖고 있기 때문이다.

## §4. 설계

### 4-0. 설계의 사실 기반 (이 계약이 새로 확인한 것 포함)

- **위임 배경과 매트릭스가 어긋났던 지점을 1차 문서로 해소했다**: 매트릭스 C10 행은 *「periodType=최종수정일(코드가 이미 사용 중)」*이라 적었으나, `search_products`(naver.py:678~)가 실제로 보내는 body는 `page`/`size`/`productStatusTypes`/`searchKeywordType`/`channelProductNos`뿐 — **요청 기간 필터가 없다**(08-20 코드 실측). 코드가 쓰는 것은 응답 필드 `modifiedDate`·`regDate`다. 「이미 사용 중」의 출처인 ref 75의 좌표 `naver.py:583`은 실제로는 **정산 endpoint**(`/v1/pay-settle/settle/case`)의 `periodType` docstring 자리다 — 다른 endpoint의 같은 이름 파라미터가 섞인 것.
- **그러나 필터 자체는 실재한다**: 공식 문서 `post-v1-products-search.md`(apicenter.commerce.naver.com/llms/, **2026-08-20 직취**, HTTP 200)에 요청 body `periodType`(`PROD_REG_DAY`/`SALE_START_DAY`/`SALE_END_DAY`/**`PROD_MOD_DAY`**) + `fromDate`/`toDate`(`yyyy-MM-dd`, **일 단위**)가 명시돼 있다. ⇒ 위임문이 [미상]으로 지정한 설계 분기(「요청 단계에서 최종수정일로 좁힐 수 있는가」)는 **「좁힐 수 있다(일 단위)」로 확정**. 단 `modifiedDate`가 어떤 변경에 전진하는지는 여전히 [미상]이라 §2-2대로 보조 검증용이다.
- 페이징: `size` 최대 500, `totalPages`·`last` 플래그 반환. 문서는 size 100~200 시작을 권고(응답 지연) — 우리 규모(1,000 안팎)에선 200으로 시작해 실측으로 조정한다.
- 응답 grain: `contents[]`(원상품) ⊃ `channelProducts[]`(채널상품). **저장 grain = 채널상품**(`channel_product_no`) — `mall_product_id`·`naver_product_bep.channel_product_id`와 같은 키 공간(전제 — [미상] 상속, §8).

### 4-1. 설계 분기표 — 폴링 주기 × diff 저장 그레인

| 분기 | 선택지 | 대가 | 판정 |
|---|---|---|---|
| **폴링 주기** | **㉮ 일 1회** | API 2~3콜/일. 일중 변경(당일 내 가격 왕복 등)은 못 본다 | ★**채택** — 소비처(밴드·BEP·일 배치)가 전부 D-1 grain이고, 일중 해상도의 소비자가 현재 0이다 |
| | ㉯ 시간당 | 48~72콜/일. 일중 가격·재고 추적 가능 | 기각 — 소비자 없는 해상도는 비용만 낸다. 필요해지면 주기만 조이면 되는 설계로 둔다(코드는 주기 무관) |
| | ㉰ 주 1회 | 2~3콜/주 | 기각 — 변경 감지 지연 최대 7일. 창을 여는 목적과 상충 |
| **diff 그레인** | ㉠ 현재 단면만(upsert) | 이력 0 — 「언제 바뀌었나」를 영영 모른다 | 기각 — 창을 여는 것이 §0의 제1 근거인데 이력이 없으면 창이 아니다 |
| | **㉡ 현재 단면 + 변경분 이력** | 이력 증가량이 실제 변경률에 비례([미상] — 첫 주 관측) | ★**채택** — D-NAO-198 전례(퇴화 행 미적재)와 디스크 93% 제약에 부합 |
| | ㉢ 전건 일일 스냅샷 | ~0.3–0.5MB/일 ≈ 110–180MB/년, 대부분 무변경 중복 | 기각 — D-NAO-198이 실측으로 기각한 모양의 재판 |

**추천 = ㉮×㉡: 일 1회 전건 폴링(필터 없이 전 상태) → 현재 단면 upsert + 변경 필드만 이력 append.**

### 4-2. 테이블 (이름은 이 계약의 발명 — 구현 시 관례에 맞춰 조정 가능)

- **`naver_product_meta_current`** (현재 단면, 1상품 1행 upsert): `channel_product_no`(PK 성격, unique) · `origin_product_no` · `group_product_no` · `name` · `status_type` · `sale_price` · `discounted_price` · `stock_quantity` · `whole_category_name` · `image_url` · `reg_date` · `modified_date` · `raw_json`(응답 원문 — 교훈 #315 방어) · `first_seen_at` · `last_seen_at` · `last_changed_at`.
- **`naver_product_meta_change`** (변경 이력, 변경 있을 때만 append): `channel_product_no` · `observed_at` · `changed_fields`(JSON: {필드: [old, new]}) · 폴링 완주 여부와 무관하게 **관측 시각은 폴링 시각이지 변경 시각이 아니다**를 컬럼 주석에 명시(폴링 grain이 일 1회라 변경 시각은 ±1일 불확실 — 이걸 숨기면 나중에 시간축 분석이 오독한다).
- 전건 폴링에서 **사라진 상품**(전회 있었는데 이번 응답에 없음)은 삭제하지 않고 `last_seen_at` 정체로 관측한다 — 삭제 판정은 `productStatusTypes` 의미론 확인([미상] ⑤) 뒤로 미룬다.

### 4-3. 크론·경로

- 잡 이름 `sync_naver_product_meta`, 슬롯 **`55 9 * * *`**(09:55 KST — 09:35 targets·09:50 baseline 뒤 빈 슬롯. ★이 슬롯 선택은 이 계약의 발명이다. 교훈 #326: 크론 슬롯은 배포 전에만 무료로 고칠 수 있다 — 승인 시 확정할 것).
- 클라이언트: `search_products`에 `period_type`/`from_date`/`to_date` 파라미터를 **additive**로 추가(기본 None — 기존 호출부 무영향). 수집기는 필터 없이 전건 순회.
- 완주 판정: 마지막 페이지 후 `수집 행수 == totalElements` 불일치 시 해당 회차를 실패로 표면화(부분 적재를 success로 기록하지 않는다 — 교훈 #318·#320).

### 4-4. 검산 등식 (합격기준 ⓑ의 원료)

1. `naver_product_meta_current` 행수 == 같은 시점 API `totalElements` (라이브 재현 가능).
2. 밴드 교차표의 Σ(밴드별 행수) + 미조인 행수 == current 총행수 (배분하지 않는다 — D-NAO-194 fan-out 원칙 승계).

## §5. 합격기준 — 라이브 증거 시나리오

★**관측 «기회» 계산**(교훈 #331 — 같은 함정에 두 세션 연속 걸렸다): 크론 09:55의 첫 발화는 배포 다음 날이라 **착수 세션 안에 오지 않는다.** 따라서 ⓐⓑⓒ는 **배포 직후 수동 트리거 1회**(기존 잡들의 수동 트리거 경로 재사용)로 같은 세션에서 관측하고, **크론 자동 발화는 합격기준이 아니라 «다음 세션 5초 확인» 이월 항목**으로 분리한다(ⓔ류 미달의 재생산을 구조로 차단).

- **ⓐ prod 라이브 행**: `naver_product_meta_current` 행수 ≥ 700(행수·수집 시각 병기 — **0행이면 미달**. 700은 adgroup_product distinct 702의 하한 근사이며 실제 기대값은 totalElements [미상]에 종속) + `naver_product_meta_change` 첫 회차는 전건 신규라 0행이어도 정상(신규 insert는 변경이 아니다 — 이 판정을 명시).
- **ⓑ 검산 등식 라이브 재현**: §4-4의 ① — 수동 트리거 직후 API 재호출 1회의 `totalElements`와 prod 행수 대조, 불일치 0.
- **ⓒ 등급 교차 산출물 + 재현 SQL**: 밴드(`band_group_total` 정본 CSV) × 상품 메타(status_type·카테고리 1단·가격대) 현재 단면 교차 1표 + **`mall_product_id` ↔ `channel_product_no` 조인율 %**(양방향: 광고 상품 중 메타 매칭 % / 메타 중 광고 등재 %) — 재현 SQL 파일 병존. ★이 표는 «단면»이지 연관 판정이 아니다 — A/B/C 판정을 내리지 않는다.
- **ⓓ 매트릭스 반영**: C10 행을 「호출가능·미적재 → 교차완료(단면)」로 갱신(개정 N — 번호는 그때 확인) + 진도 5/5 병기 + **「완료 ≠ 모든 데이터」 문구 병기**(D-NAO-200 종료 게이트) + 층1 커머스 실사용 카운트 갱신.
- **이월 관측(합격기준 아님, HANDOFF 의무 기재)**: 익일 09:55 크론 자동 발화(`scheduler_state.last_run_at`) + 첫 실변경 감지 시 `change` 행 생성.
- 완료 QA는 별도 Sonnet·읽기 전용, 선판정 2개 먼저(D-NAO-200) — 「전수 조사 완료」 문구 금지.

## §6. 배포 절차 (`--migrate` 강제 순서) · 롤백

```bash
# 0) 사전: git branch --show-current 확인 · ./scripts/next_ids.sh · prod 디스크 재측정
# 1) 테스트: cd backend && python3 -m pytest tests/ -q -p no:randomly
# 2) 배포 — 마이그 파일을 목록에 포함하고 --migrate (강제 순서: ①마이그 배포 → ②원격 alembic upgrade head → ③코드 배포 → ④재시작)
scripts/safe_deploy.sh \
  backend/alembic/versions/<rev>_c10_product_meta.py \
  backend/app/models.py \
  backend/app/clients/naver.py \
  backend/app/services/<수집기>.py \
  backend/app/services/scheduler_service.py \
  --migrate --restart
# 3) 수동 트리거 1회 → §5 ⓐⓑ 관측 → ⓒⓓ 산출
```

**롤백**: ①크론 정지 = `scheduler_state.is_enabled=0`(즉시, 코드 무변경) ②코드 원복 = 이전 커밋 파일을 `safe_deploy.sh`로 재배포(추가 컬럼이 아니라 **추가 테이블**이라 구코드를 깨지 않는다 — nullable 컬럼 사고의 모양 아님) ③테이블 제거가 필요하면 순서 역전: 코드를 먼저 내리고 alembic downgrade(구코드를 깨는 방향의 마이그레이션은 `--migrate`를 쓰지 않고 수동 조율 — 프로젝트 CLAUDE.md 원문). 적재분 데이터는 additive라 방치 무해.

## §8. [미상] · 착수 첫 확인 항목 · Jino 질문

**[미상]으로 남기는 것** (추정으로 채우지 않았다):
1. **응답 `channelProducts` 하위의 전체 필드 목록** — llms 문서가 「하위 구조 생략(OAS 참조)」. 누적판매·리뷰 필드 실림 여부 포함. ⇒ **구현 착수 시 첫 확인 항목**: 실응답 1페이지(읽기 전용 POST 조회)로 필드 전수 확인 후 컬럼 확정. raw JSON 보존이 이 [미상]의 방어다.
2. **`modifiedDate` 갱신 의미론** — 어떤 변경(재고 자동 감소 포함?)이 이 값을 전진시키는가. 전건 폴링 채택으로 설계 의존은 없앴고, 첫 주 diff 관측이 간접 답을 준다.
3. **`channelProductId ≡ mall_product_id` 동일성** — 인계 [미상] 상속. 이 계약은 확정하지 않고 조인율 %만 실측한다(ⓒ).
4. **totalElements 실값**(= 카탈로그 실규모) — 758·702는 하한 정황. 수동 트리거 1회가 확정한다.
5. **`productStatusTypes` 무필터 호출의 포함 범위**(DELETE 상태 포함 여부) — 문서 enum엔 DELETE가 있으나 무필터 기본 동작 미기재. 첫 호출에서 상태 분포로 확인.
6. **change 테이블 증가율** — 첫 주 관측 후 상한 기록(§7).

2. **크론 09:55 슬롯 확정** (§4-3 — 배포 후엔 수정 비용이 붙는다, 교훈 #326)
